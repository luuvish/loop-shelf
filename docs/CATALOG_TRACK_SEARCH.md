# 현재 수록곡의 로컬 검색

2026-10-25. `CatalogTrackSearchStore`와 `GET /api/catalog/tracks`는 이미 관리 중인 **합성 카탈로그의 현재 채택된 수록곡**을 검색합니다. 서비스·인증 API와 연속 페이지 조회에 [React 검색 화면](CATALOG_TRACK_UI.md)을 연결했습니다. 외부 검색/수집·live 활성화·별칭 생성·개인 저장·음원 재생을 수행하지 않습니다. 새 설치에 관리 자료가 없으면 정상 0건입니다.

## API와 검색어

실제 로그인 쿠키와 필수 `X-LoopShelf-Session`이 필요합니다. 누락/만료/위조 인증은 401, 세션 조건 누락은 428, 현재 쿠키와 조건 불일치는 401입니다. 기존 카탈로그 읽기처럼 인증과 동기 검색은 하나의 `withDatabase` 경계에서 실행합니다. 네트워크 대기나 소스 요청은 없습니다. 외부 검색/상세/저장의 요청 예산과 구별되는 로컬 카탈로그 읽기이며, 동시성·다중 프로세스·대규모 요청 부하 검증은 포함하지 않습니다.

| 입력 | 계약 |
| --- | --- |
| `q` | 필수, 입력/정규화 후 각각 최대 200 UTF-16 코드 단위. 빈 값·공백만 있는 값·제어/형식 문자는 거절 |
| `sourceId` | 생략 또는 `khinsider` / `zophar` |
| `limit` | 기본 12, 정수 1–100 |
| `offset` | 생략 시 0, 정수 0–100,000. `cursor`와 함께 전달할 수 없음 |
| `cursor` | 직전 응답의 `nextCursor`, 최대 384자. 검색어/출처/페이지 크기는 이전과 동일해야 함 |

예: `/api/catalog/tracks?q=%E8%A8%98%E6%86%B6&sourceId=zophar&limit=12&offset=0`. 다른 필드·반복 query·임의 URL/userId/자료 종류는 허용하지 않습니다. 검증 실패는 400입니다. 조회 실패/보관 정리 충돌은 오류이며 성공 0건으로 바꾸지 않습니다.

현재 채택한 **곡 제목만** NFKC → 소문자 → 연속 공백 정리 → 양끝 공백 제거 후 리터럴 부분 검색합니다. 한글·일본어 1–2자도 같은 규칙이며 분리된 한글 자모는 NFKC로 조합되는 범위에서 일치합니다. `%`, `_`, 따옴표, `*`는 검색 구문이나 와일드카드가 아닙니다. 토큰 AND/OR, 발음·로마자·번역·추측 별칭, 앨범/게임 제목 검색은 제공하지 않습니다. 개인 제목·메모·즐겨찾기·미연결 항목도 검색하지 않습니다.

정렬은 정규화 곡 제목 → source ID → 앨범 원본 키 → **현재 binding 위치** → Track UUID입니다. 제목이나 표시 번호가 같은 행을 합치지 않습니다. 한 행 더 읽어 다음 페이지 유무를 확인하며 전체 건수/전체 페이지 수를 추측하지 않습니다.

## 연속 페이지와 변경

첫 요청에 `q`/선택한 `sourceId`/`limit`을 보내고, 다음 요청에 동일한 조건과 응답의 `nextCursor`를 `cursor`로 전달합니다. 정규화 결과가 같은 검색어는 동일한 조건입니다. 마지막으로 본 곡의 정렬값보다 큰 행을 읽으며 매번 앞의 행을 다시 건너뛰지 않습니다. `nextCursor: null`은 해당 조회 시점에 다음 결과가 없다는 뜻입니다. 임의 페이지 번호로 바로 이동하는 계약은 아닙니다.

커서는 버전·공용 Track UUID·검색 조건 해시·기준 행 해시만 담은 base64url 문자열입니다. 곡/앨범 제목·출처 키·관찰 원문·개인 정보·계정/세션·오디오 URL을 복사하지 않습니다. 해시는 서명이 아니며 커서는 인증·권한·고정 스냅샷을 제공하지 않습니다. 매 요청의 실제 쿠키/세션 조건이 필요하며, 같은 공용 자료를 보는 다른 인증 계정도 같은 커서를 쓸 수 있습니다. 서버 메모리/별도 DB 테이블에 저장하지 않아 재시작 뒤에도 현재 자료가 같으면 동작합니다.

형식·버전·필드·길이 오류, 다른 검색어/출처/limit, `cursor`와 `offset` 동시 입력(0도 포함)은 400 `invalid_input`이며 보관 정리 전에 거절합니다. 유효한 형식이라도 현재 기준 행을 다시 찾을 수 없거나 정렬/채택 근거가 바뀌면 409 `cursor_invalidated`입니다. 자동으로 첫 페이지를 반환하지 않으며 사용자가 새 검색을 선택해야 합니다. 커서 자체에는 시각 기반 만료가 없지만 자료의 가용성·보관 기한·정책은 매번 재검사합니다.

보관 정리 뒤 같은 읽기 트랜잭션에서 기준 곡의 제목·출처/앨범 키·현재 위치·UUID와 채택 관찰을 확인합니다. 삭제·차단·누락·만료·자료 종류 변경이나 명시적 재채택은 연속 조회를 무효화합니다. 미채택 새 관찰만 생기면 기존 목록을 유지하며 최신 검토 상태를 반환합니다. 개인 메모/제목 변경은 검색 순서에 영향을 주지 않습니다. 기준 곡 외의 행도 매번 현재 가용성/관찰로 읽으므로 새로 제거/만료된 내용은 노출하지 않습니다. 보관 정리 충돌은 기존 409 오류를 유지합니다.

여러 페이지 전체를 고정하지는 않습니다. 페이지 사이에 기준 곡보다 앞에 새 곡이 생기면 현재 연속 조회에는 포함되지 않으며, 뒤에 생긴 곡은 다음 결과에 포함될 수 있습니다. 다른 곡의 재채택/정렬 변경으로 건너뛰거나 다시 보일 수 있으므로 화면은 페이지를 교체하고 새 검색으로 갱신해야 합니다. 고정 자료에서의 순회는 같은 제목/반복 번호도 중복·누락 없이 보존합니다.

기존 offset 조회도 호환성을 위해 유지합니다. 다음 offset이 100,000을 넘으면 `nextOffset: null`, `paginationLimited: true`이지만 `nextCursor`로 계속 읽을 수 있습니다. 이 표시는 offset 방식의 범위 제한이며 전체 결과 소진이 아닙니다. 범위 내 큰 offset이 실제 결과 수를 넘으면 정상 빈 페이지입니다. 커서 요청에서는 `nextOffset: null`, `paginationLimited: false`이며 다음 이동에는 `nextCursor`만 사용합니다. React 화면은 커서 방식을 사용합니다. 양수 offset은 0016의 현재 검색 순서로 페이지를 선택하고 같은 읽기 트랜잭션에서 전체 원본 근거를 재검사합니다. 목록과 선택 행이 불일치하면 오류이며 정상 0건/부분 성공으로 바꾸지 않습니다.

## 응답과 근거

공유 타입은 `src/shared/catalog-track-search.ts`입니다. 봉투는 `sampleKind: synthetic`, `identity: source-provisional`, 정규화된 `query`, 선택한 `sourceId` 또는 null, 읽기 시작 시각 `checkedAt`, `items`, `nextCursor`, `nextOffset`, `paginationLimited`입니다.

각 항목은 Track UUID·현재 제목·현재 위치·표시 번호·디스크 표기·길이와 채택 관찰의 ID/취득 시각/파서 버전/보관 기한을 담습니다. null 길이는 미확인이고 0ms와 구별합니다. 앨범에는 Album UUID·현재 제목·원래 SourceEntity ID/소스/원본 키/페이지 URL과 **앨범 제목을 채택한 별도 관찰 근거**, 트랙 검토 상태를 담습니다. 앨범 제목 근거와 곡 목록 근거는 서로 다른 관찰일 수 있습니다. 출처 키/URL은 소속 앨범의 것으로, 트랙 SourceEntity나 오디오 주소를 만들어 내지 않습니다.

개인 ID·제목 override·메모·즐겨찾기·저장 여부는 포함하지 않으며 검색 SQL은 개인 테이블을 읽지 않습니다. 같은 공용 자료를 보는 두 계정은 같은 항목을 받습니다. 기존 Album 검색/카탈로그 탐색 응답은 변경하지 않았고 통합 외부 검색 응답에 합성 트랙을 섞지 않습니다.

응답은 `Cache-Control: no-store`, `Vary: Cookie, X-LoopShelf-Session`과 인증된 사용자/세션 헤더를 사용합니다. 세션 헤더는 인증 수단이 아닙니다. React 화면은 현재 쿠키와 응답 조건도 확인하고 이전 결과/기한 만료와 취소를 처리합니다. `checkedAt`은 읽기 스냅샷의 시각이며 외부 사이트의 현재 가용성을 재확인한 시각이 아닙니다.

## 현재 목록과 수명

- 관리 SourceEntity가 synthetic이며 앨범 Entity·현재 제목 관찰·채택 곡 목록 관찰이 active인 자료만 읽습니다. 소스는 unverified/available이어야 하며 unverified를 이용 허가로 해석하지 않습니다.
- 현재 `catalog_track_binding`에 있고 Track Entity가 active인 행만 검색합니다. 제거 영수증·차단·없는 페이지·누락 곡·미채택 새 곡·미연결 개인 자료는 제외합니다. `track.position`을 현재 수록 위치로 쓰지 않습니다.
- 새 관찰의 변경 목록이 검토 중이면 기존 채택 목록을 `review_required`로 표시합니다. 원본 키 없는 곡을 이름/길이로 자동 대응하지 않습니다. 명시적 채택 이후에만 새 제목·순서·누락을 반영합니다.
- 검색 전에 보관 정리를 수행합니다. 만료/정책 철회는 개인 UUID/내용을 유지하면서 검색에 사용할 외부 텍스트를 정리합니다. 첫 origin 관찰이 만료되어도 현재 채택 관찰이 유효하면 그 근거의 곡을 검색할 수 있습니다. 반대로 앨범 제목만 새로 취득해도 만료된 트랙 baseline을 되살리지 않습니다.
- 보관 정리에 공유/수동 내용 충돌이 있으면 409를 반환하고 검색 결과를 노출하지 않습니다. stale 결과나 성공 0건으로 대체하지 않습니다. 원본 HTML·캐시 복사본·개인 검색 인덱스로 우회하지 않습니다.

## 조회와 검증

첫 측정은 트랙마다 앨범·관찰을 반복 조회하는 구조였습니다. 기존 전체 경로는 검색 가능한 앨범과 채택 관찰을 먼저 한 번 확인하고, 관찰별 binding 인덱스로 현재 곡만 읽습니다. 제목/출처/현재 위치로 페이지를 결정한 뒤 해당 페이지의 전체 응답을 조립합니다. 전체 Entity나 과거 binding을 먼저 훑지 않습니다. 최초/앨범별 조회 개선의 측정이 목표를 넘어서 0014의 `catalog_track_search_title_idx` 표현식 인덱스를 추가했습니다. 인덱스는 정규화 제목·앨범 UUID·Track UUID를 담고 검색은 현재 binding과 가용성을 별도로 검사합니다. 0014 당시에는 SQLite가 채택/만료/제거 시 Track 행과 함께 인덱스를 갱신하며 별도 검색 문서 복사본이나 FTS는 추가하지 않았습니다. 연속 조회는 기준 곡을 UUID로 다시 확인한 뒤 0014 인덱스의 제목 범위 검색과 전체 정렬 튜플 비교로 이어 읽습니다. 커서의 전체 조회 경로는 SQL OFFSET을 사용하지 않으며 연속 페이지 도입 당시에는 새 인덱스/마이그레이션이 없었습니다. 이후 양수 offset은 0016의 파생 순서와 원본 재검사로 개선했습니다. [측정 조건과 결과](CATALOG_PERFORMANCE.md)

`tests/catalog-track-search.test.ts`는 다국어/짧은 검색어·엄격한 입력·반복 번호/미확인 값·순서/페이지·개인 정보 비노출, 변경 관찰/명시적 채택·누락/제거/차단·만료/정책 철회·실행 계획과 실제 쿠키 세션의 인증/재확인/오류를 검증합니다. 0014 단계는 신규 19개를 포함한 Node 410개와 브라우저 회귀 17개를 통과했습니다. 이후 연속 조회 10개를 추가하고 복원 테스트에도 기존 커서 이어 읽기를 포함해 strict 타입·빌드·전체 Node 420개를 통과했습니다. 고정 자료 전체 순회·정규화 동등 조건·입력 경계·변경/만료/충돌·실행 계획·실제 계정/세션과 DB 대기 후 재확인을 검사했습니다. 연속 페이지 API 단계에서는 화면 변경이 없어 브라우저 검사를 다시 실행하지 않았습니다. 이후 수록곡 검색 화면을 추가했으며 그 검증은 [화면 계약](CATALOG_TRACK_UI.md)에 별도로 기록합니다.

## 0014 업그레이드와 복원

기존 적용 SQL은 변경하지 않고 `0014_catalog_track_search.sql`을 추가합니다. 운영 절차대로 백업 후 `npm run db:migrate`를 실행해야 합니다. 기존 UUID·내용·관찰·개인 버전은 바뀌지 않습니다. 실패한 pending 배치는 인덱스와 이력까지 롤백합니다. 이전 앱은 새 마이그레이션 이력을 보고 시작을 거절합니다.

표현식 인덱스에는 결정적인 `normalize_search` 함수가 필요합니다. 일반 DB뿐 아니라 백업 복사본·읽기 전용 복원 원본에도 같은 함수를 등록한 뒤 무결성 검사와 보관 정리를 수행합니다. 복원은 새 경로에만 하고 기존 세션/임시 토큰을 제거합니다. 원본 DB/백업은 수정하지 않습니다. 정규화 규칙 또는 런타임의 Unicode 동작이 바뀌는 업그레이드는 인덱스 재생성 마이그레이션과 검색/복원 재검증을 함께 검토해야 합니다.

React 화면은 `nextCursor`를 이용하고 409에서 자동 재전송 없이 새 검색을 안내합니다. 화면의 사용/세션/보관/검증은 [화면 계약](CATALOG_TRACK_UI.md)에 기록합니다. 기존 offset 개선은 [0016 검증](CATALOG_OFFSET_SEARCH.md)에 기록하며 배포 동시 부하와 실제 소스 연동은 별도 미완료입니다.


후속 점유 비용 개선에서는 offset 0/커서의 첫 일치 제목과 정렬상 앞선 출처 256개로 limit+1행을 확보할 수 있을 때만 작은 조회 결과를 사용합니다. 부족하면 전체 정렬 순서의 곡 후보 최대 256개를 보조로 읽고 해당 앨범의 전체 근거를 검사합니다. 이 경로는 적격 limit+1행을 확보하거나, 적격 행이 있으면서 같은 CTE의 원시 후보가 256 미만임을 확인한 경우 사용합니다. 후자는 남은 후보 전체를 검사한 짧은 마지막 페이지입니다. 정확히 256개 또는 카운터를 받지 못한 빈 결과는 기존 전체 조회로 돌아가며 256을 결과 상한/소진 판정으로 쓰지 않습니다. 같은 트랜잭션의 관찰/현재 binding·커서 기준/보관/권한을 유지합니다. 0016은 양수 offset용 현재 검색 순서를 SQLite trigger로 동기화합니다. 정규화 제목을 포함하는 파생 목록이므로 만료/제거 시 함께 정리하며 개인 내용은 복사하지 않습니다. 앱 시작/백업/복원에서 원본 view와 전수 비교하고 운영자는 `catalog:reindex`로 재생성할 수 있습니다. 선택 페이지의 재검사만으로 인덱스에서 누락된 모든 행까지 탐지하는 것은 아닙니다. 정상 쓰기 동기화·전수 검사의 역할과 유지보수 비용은 [전용 문서](CATALOG_OFFSET_SEARCH.md)를 따릅니다. 위 0014/커서 도입 당시 설명은 해당 단계의 구조입니다.
