# 북마크 삭제 후 되돌리기

구현·검증일: **2026-10-22**. 직접 입력한 단독 북마크의 삭제 후 60초 동안 원래 항목을 복구합니다. 연결된 대표·멤버는 기존처럼 먼저 연결을 해제해야 삭제할 수 있습니다.

## 화면에서 사용

삭제 확인 후 선반의 **삭제한 북마크 → 되돌리기**를 누릅니다. 원래 북마크 ID·Entity ID, 제목, 주소, 메모, 즐겨찾기와 생성/수정 시각을 복구합니다. 검색 인덱스도 함께 복원합니다. 수정 버전은 새로 부여하므로 삭제 전에 열어 놓은 오래된 편집 창은 저장할 수 없습니다.

여러 항목의 복구 안내를 각각 표시하며 남은 시간을 보여줍니다. 시간 만료 시 버튼을 비활성화하고 안내를 닫을 수 있습니다. 닫기·새로고침·창 닫기·로그아웃/세션 전환 후에는 해당 창의 복구 안내를 다시 불러오지 않습니다. 휴지통이나 장기 복구 목록은 아닙니다. 중요한 데이터는 JSON 내보내기 또는 운영자 DB 백업을 사용합니다.

다른 창에서 같은 주소를 새로 저장했거나 원래 ID를 JSON으로 복원했다면 기존 항목을 덮어쓰지 않고 충돌을 안내합니다. 현재 선반을 다시 불러오며 복구 안내는 남은 시간 동안 유지합니다. 다른 계정의 내용은 보여주지 않습니다.

삭제 응답을 받지 못했다면 같은 삭제 대화상자의 버튼으로 다시 확인합니다. 복구 응답을 받지 못했다면 같은 되돌리기 버튼으로 재시도할 수 있습니다. 이미 처리된 요청은 다시 적용하지 않습니다. 오프라인 요청을 예약하거나 자동 전송하지 않으며, 오프라인 상태에서도 서버의 60초 기한은 연장되지 않습니다.

## API와 소유권

모든 요청은 실제 로그인 쿠키와 정확한 Origin이 필요하고 응답은 `no-store`입니다. `X-LoopShelf-Session` 사전 조건도 기존처럼 검증합니다. 복구 권한은 **삭제한 사용자와 로그인 세션**에 묶입니다. 같은 사용자가 다시 로그인한 다른 세션도 기존 삭제를 되돌릴 수 없습니다. 운영자의 전체 DB 복구는 복원본의 모든 세션과 삭제 복구 영수증을 제거합니다. 일반 서버 재시작은 유효한 영수증을 유지합니다. [운영 복구 절차](OPERATIONS.md)

| 요청 | 본문 / 결과 |
| --- | --- |
| `POST /api/bookmarks/:id/deletion` | `{ version, operationId }`. 클라이언트가 새 UUID를 만들고 결과가 불확실한 재시도에는 그대로 사용. 200 `{ id, bookmarkId, expiresAt, remainingMs, state }` |
| `POST /api/bookmark-deletions/:id/restore` | `{}`. 200 `{ bookmarkId, restored }`. 최초 복구는 `true`, 이미 처리된 요청은 `false` |
| 기존 `DELETE /api/bookmarks/:id` | 기존 204 영구 삭제 계약 유지. 복구 정보는 만들지 않음. 이전 앱 버전과 API 클라이언트 호환용 |

복구 영수증에는 메모·URL·사용자/세션 ID를 포함하지 않습니다. `operationId`는 인증 수단이 아니며 같은 ID를 다른 북마크/버전에 재사용하면 거절합니다. 영수증 ID를 알아도 다른 사용자나 로그인 세션에서는 조회·복구할 수 없습니다. 같은 삭제 요청을 재시도해도 기한을 갱신하지 않습니다.

- `undo_unavailable` / 404: 기한 만료·존재하지 않는 영수증·다른 사용자/세션. 다른 계정의 존재를 구분하지 않음.
- `undo_conflict` / 409: 같은 소스 주소 또는 내부 ID가 이미 사용 중. 기존 내용은 변경하지 않음.
- `undo_limit` / 409: 사용자당 유효 영수증 20개 제한. 복구를 마친 재시도 방지 기록도 만료까지 포함하며 이 경우 새 삭제는 실행하지 않음.
- 버전 충돌·연결된 항목 보호, 입력/Origin/세션 오류는 기존 API 계약을 따름.

## 저장·만료·트랜잭션

`0005_bookmark_deletions.sql`은 짧게 유지하는 `bookmark_deletion` 테이블을 추가합니다. 실행 전에 `npm run db:migrate`를 적용합니다. 기존 마이그레이션이나 북마크 값은 수정하지 않습니다.

삭제 시 서버가 읽은 원본 스냅샷을 저장하고, 일반 라이브러리 행·북마크 Entity·검색 인덱스를 같은 immediate 트랜잭션으로 제거합니다. 삭제된 내용은 목록·검색·JSON export에 나오지 않습니다. 클라이언트가 복구 내용을 제출하거나 임의 소유자를 지정할 수 없습니다.

복구 트랜잭션은 소유자·세션·기한·중복 주소·전역 ID 충돌을 확인한 다음 원래 행을 삽입합니다. `library_revision` 상한보다 큰 버전을 할당하고, 영수증을 `restored`로 바꾸면서 스냅샷 내용을 바로 비웁니다. 실패하면 행·검색·버전·영수증 변경 전체를 롤백합니다. 이미 복구한 영수증으로는 이후 편집을 덮어쓰거나 다시 삭제된 항목을 되살릴 수 없습니다.

서버 시간으로 60초가 지나면 복구를 거절합니다. 만료 행은 서버 시작 시, 삭제/복구 요청 전, 실행 중 10초 간격으로 제거합니다. 정리 작업도 `withDatabase`로 인증·저장 작업과 직렬화합니다. 로그아웃/비밀번호 초기화 등으로 해당 세션 행을 삭제하면 FK cascade로 영수증도 제거합니다. 서버 중지 중에는 정리 작업이 실행되지 않으며 다시 시작할 때 만료 행을 제거합니다.

이는 활성 DB 행의 보관 기한입니다. 이미 생성한 DB 백업에는 당시의 임시 스냅샷도 포함될 수 있으며 기존 백업 보관 정책을 따릅니다. 브라우저에는 안내용 제목·영수증을 메모리로만 유지하고 localStorage·IndexedDB·Service Worker에 저장하지 않습니다. 서버 기한이 최종 기준이며 화면은 응답 왕복 시간을 보수적으로 뺀 남은 시간을 사용합니다.

## 검증

- 실제 두 계정과 별도 로그인 세션: 소유권, 세션 조건, Origin, 입력 위조, 로그아웃 시 제거, 동시에 요청한 복구의 단일 적용.
- DB: ID·내용·시각·검색 보존, 새 버전과 오래된 편집 거절, 삭제/복구 재시도, 이후 재삭제의 부활 방지, URL/ID 충돌, 정확한 만료 경계, 20개 상한, 실패 롤백, 0004 → 0005 업그레이드.
- 서버 재시작: 유효한 영수증의 복구와 만료된 임시 내용의 시작 시 정리.
- 데스크톱 1440×1000·모바일 360×800 Chromium: 삭제 및 복구 응답 유실 후 재시도, 이중 클릭, 원래 내용 복원, 새 주소 충돌 후 최신 선반 표시, 만료 안내·버튼 비활성화, 로그아웃 후 안내 제거. 화면 만료 테스트에서는 응답의 표시용 남은 시간만 짧게 만들었으며 실제 서버의 60초 경계는 DB 테스트로 검증했습니다.

전체 검증은 타입 검사·빌드·Node 테스트 **134개**, 기존 흐름을 확장한 브라우저 시나리오 **11개**입니다. 외부 음악 사이트 요청과 운영 DB 변경은 없습니다.
