# 소스 요청 제한의 영속화와 프로세스 간 조정

2026-10-25. 0017은 같은 로컬 SQLite 파일을 사용하는 프로세스들의 소스 요청을 조정합니다. 자체 기본 제한의 구현이며 사이트가 허용한 quota를 의미하지 않습니다. 제품 정책 unknown·robots/path 검토 gate는 유지하고 실제 KHInsider/Zophar 요청은 수행하지 않았습니다.

## 적용 범위

제품 Adapter는 `getSourceCapture(db)`를 사용합니다. 같은 연결에서는 인스턴스를 재사용하고 서로 다른 연결/프로세스는 DB의 같은 소스 행·대기열로 조정합니다. 미연결 `captureSourcePage`는 계속 정책 비활성이며 내부 live 드라이버도 coordinator가 없으면 실행하지 않습니다. 허용 판정·시계·DNS/HTTP 대체는 내부 합성 테스트 경계에만 존재합니다. HTTP/env로 정책·DB·자료 종류를 교체하지 않습니다.

정책 검사가 예약보다 먼저 실행되므로 현재 비활성 제품 호출은 DB 예약·DNS·HTTP를 만들지 않습니다. 정책이 미래에 허용으로 바뀌어도 robots/path 검토가 구현되기 전의 고정 거절은 유지합니다. 기존 IP 고정·TLS·같은 리소스 redirect·크기 상한·캐시/표시 정책은 바꾸지 않습니다.

## 저장하는 상태

| 테이블 | 내용 |
| --- | --- |
| `source_request_state` | 고정 source ID, 다음 시도 가능 시각, 429 cooldown 종료 시각, 최근 확인한 시각 |
| `source_request_ticket` | DB 할당 순번, 무작위 예약 token·프로세스 인스턴스 owner ID, source ID, 호출 기한, 단계 |

URL·검색어·계정·쿠키·HTML·개인 내용은 저장하지 않습니다. token은 운영 예약 식별자이며 인증이나 사용자 선택 수단이 아닙니다. 기존 공용/개인 음악 UUID를 만들거나 바꾸지 않습니다. 소스별 최대 하나의 `reserved`/`running` 행을 부분 UNIQUE 인덱스로 검사합니다.

## 예약·시도·완료

| 단계 | 의미 | 만료/취소 |
| --- | --- | --- |
| `waiting` | DB 순번으로 대기. 소스당 holder 외 최대 8개 | 만료 시 제거 가능. 취소는 자기 token만 정리 |
| `reserved` | 해당 호출의 순서 확보. 아직 DNS/HTTP를 시작하지 않음 | 기한 경과 후 다른 요청이 제거 가능. 이전 소유자는 시작 전 token/기한을 다시 검사 |
| `running` | 원자적으로 이 단계로 바꾼 뒤 DNS/HTTP 시도 | **기한만으로 자동 해제하지 않음**. 실제 시도 종료와 대기 시각 저장이 확인되어야 해제 |

전체 호출 예산은 기존 10초이며 예약·DB 큐·간격·DNS·본문·redirect가 모두 포함됩니다. DB에는 남은 호출 예산으로 제한한 예약 만료 시각을 기록합니다. DNS 뒤/본문 뒤에는 현재 running token·기한을 다시 검사합니다. 성공은 완료/해제 DB 작업 뒤에도 호출 기한과 정책을 확인한 후 반환합니다. HTML 취득 시각은 본문 완료 시각을 유지합니다.

완료한 시도는 다음 DNS까지 최소 3초를 DB에 기록하고 `reserved`로 돌아갑니다. redirect도 같은 token을 유지하며 각 hop의 간격·DNS/정책 검사를 거칩니다. 마지막 완료 후 예약을 제거합니다. 실패한 DNS·HTTP와 취소된 실행도 확인된 정리 뒤 간격을 적용합니다. 예약 대기는 100ms 간격으로 DB 상태를 확인하며 네트워크 요청의 자동 재시도는 하지 않습니다. 다른 소스는 독립적으로 진행합니다.

429의 초/HTTP 날짜·기본 60초·아주 긴 값 처리 계약은 [전송 문서](SOURCE_TRANSPORT.md)를 유지합니다. DB에는 이전 cooldown과 새 판단 중 더 긴 시각을 저장합니다. 대기/새 요청과 재시작한 프로세스도 같은 시각 전에는 DNS 없이 `rate_limited`를 반환합니다. 다른 프로세스에서 관찰한 429를 현재 프로세스 메모리의 오래된 값으로 덮어쓰지 않습니다.

## DB·취소·장애 경계

모든 조정 쓰기는 `withDatabase` 안의 짧은 `BEGIN IMMEDIATE` 트랜잭션입니다. 해당 작업 동안만 SQLite busy timeout을 0으로 바꾸고 반드시 이전 값으로 복구합니다. 다른 프로세스가 쓰기 잠금을 보유하면 동기적으로 5초를 기다리지 않고 실패합니다. DNS/HTTP·타이머를 기다리는 동안 DB 연결 경계를 점유하지 않습니다. 같은 프로세스의 인증 작업과도 기존 FIFO를 따릅니다.

DB 큐에서 만료/취소된 예약 작업은 실행 직전에 신호를 다시 확인해 늦게 예약을 만들지 않습니다. 이미 실행한 시도의 완료/자기 예약 정리는 큐에 남겨 수행할 수 있지만 취소 응답을 그 큐가 끝날 때까지 지연하지 않습니다. 뒤늦은 정리는 token/owner를 확인하며 다른 예약을 삭제하지 않습니다. 정리 실패를 메모리 제한으로 우회하지 않습니다.

일반 해제는 `running` 행을 삭제할 수 없습니다. 429 저장이나 완료 시각 저장에 실패하면 불확실한 running 행을 보존합니다. 성공 콘텐츠를 노출하지 않고 `network_error`(호출 기한/취소가 우선이면 해당 오류)를 반환합니다. 프로세스 강제 종료·일시 정지·이벤트 루프 지연으로 아직 실행 중일 수 있는 요청도 기한이 지났다는 이유만으로 다른 프로세스가 대체하지 않습니다. 사용 가능한 시각을 확정할 수 없어 임의 `retryAt`을 만들지 않습니다. 이 보수적 보류는 가용성보다 중복 전송 방지를 우선합니다.

응답을 관찰하기 전에 프로세스가 죽으면 그 응답에 더 긴 Retry-After가 있었는지 알 수 없습니다. 복구 명령의 기본 대기 60초만으로 충분하다고 단정하지 않으며 운영자가 소스의 요구와 불확실성을 검토해야 합니다. 네트워크 peer가 내부 작업을 끝낸 시점까지 관찰하는 계약도 아닙니다.

## 시계와 설치 범위

호출 deadline은 기존 단조 시계, 프로세스 간 시각은 같은 호스트의 epoch ms를 사용합니다. DB 최근 시각보다 뒤로 간 시계는 거절하고, 한 coordinator 수명 안에서 벽시계와 단조 시계의 차이가 1초를 넘으면 진행하지 않습니다. 시계 오류로 DB의 대기 시각을 줄이거나 초기화하지 않습니다.

전제는 신뢰할 수 있는 **같은 호스트의 시계·같은 로컬 DB**입니다. 모든 프로세스가 종료된 사이의 앞으로 이동한 시계는 이 구조만으로 판별할 수 없습니다. 부팅/시계 교정 뒤에는 저장 시각과 소스 대기 요구를 운영자가 검토해야 합니다. 여러 호스트·복제 DB·서로 다른 설치/파일·네트워크 파일시스템·공통 외부 IP의 별도 앱을 통합 제한하지 않습니다. 소스 간 같은 운영 기반의 그룹 quota, 일/월별 별도 quota, 다른 사용자 프로세스의 직접 사이트 요청도 범위 밖입니다.

1초 차이 검사는 모든 시계 교정을 검출하는 기능이 아닙니다. 안정적인 호스트 시계라는 전제 밖에서 정확한 경과 간격을 보장하지 않습니다. 시계 이상이 확인되면 worker를 중지하고 교정/검토 후 더 긴 대기를 적용합니다.

## 운영 명령

현재 설정의 DB에서 상태만 읽습니다. 원본 콘텐츠나 개인 정보를 출력하지 않습니다.

```sh
npm run source:requests -- inspect --source zophar
```

`running` 행의 기한이 지났다면 **모든 앱/작업 프로세스를 먼저 중지**하고, 실제 진행 중인 요청이 없으며 소스가 요구한 대기 시간을 검토했음을 확인합니다. `inspect`의 정확한 token과 검토한 미래 ISO 시각을 사용합니다.

```sh
npm run source:requests -- recover --source zophar --token '<INSPECTED_TOKEN>' \
  --reviewed-retry-at '<REVIEWED_FUTURE_ISO_TIME>' --confirm-workers-stopped
```

이 플래그는 운영자의 확인이며 명령이 OS의 모든 worker 중지를 자동 입증하는 것은 아닙니다. 살아 있는 worker와 병행해서 실행하지 않습니다. 정확히 일치하는 **만료된 running** 행만 해제하며, 기한 내 요청·다른 token·없는 행은 거절합니다. 검토 시각은 최소 현재+60초여야 하고 기존 더 긴 cooldown/간격은 줄이지 않습니다. 해제와 새 대기 시각은 한 트랜잭션에 반영됩니다. 과거 소유자의 늦은 완료/삭제는 새 예약에 영향을 주지 않습니다. 시간/DB 오류나 알 수 없는 소스 요구를 이 명령으로 우회하지 않습니다. 자동 실행·HTTP 복구 endpoint는 없습니다.

과거 백업 이후의 알려진 대기를 재적용할 때는 예약을 해제하지 않는 `defer`를 사용합니다. 모든 worker를 중지하고 검토한 미래 시각을 지정하며 기존보다 긴 제한만 반영합니다. 최소 현재+60초 조건은 같고 token 옵션은 거절합니다. running 보류가 있으면 별도 검토/`recover`가 여전히 필요합니다.

```sh
npm run source:requests -- defer --source zophar \
  --reviewed-retry-at '<REVIEWED_FUTURE_ISO_TIME>' --confirm-workers-stopped
```

## 업그레이드·백업·복원

0017은 기존 0001–0016을 바꾸지 않고 운영 상태 테이블/인덱스만 추가합니다. 기존 버전으로 검증된 백업을 만든 뒤 새 코드에서 `npm run db:migrate`를 실행합니다. 실패 시 스키마·이력을 함께 롤백하며 이전 코드는 새 이력의 DB로 시작하지 않습니다. 운영 DB에는 이번 개발 중 적용하지 않았습니다.

검증된 전체 백업과 새 경로 복원은 요청 상태·cooldown·running 보류를 그대로 보존합니다. 세션/임시 토큰을 지우는 복원 절차에서 이 상태를 함께 초기화하지 않습니다. 일반 재시작에서 예약을 전부 지우지 않습니다. 과거 백업에는 백업 이후의 429/요청이 없으므로 복원만으로 최신 제한을 보장할 수 없습니다. 서비스를 중지한 채 최신 제한/불확실한 요청을 따로 보존·대조하고 더 긴 대기 요구를 재적용해야 합니다. 검토가 끝나기 전 외부 요청을 활성화하지 않습니다. [전체 운영 절차](OPERATIONS.md)

## 검증

`tests/source-coordination.test.ts`와 IPC worker는 임시 DB·두 연결·실제 분리 Node 프로세스와 합성 DNS/응답만 사용합니다. 실제 TLS/실사이트/CORS 검증이 아닙니다.

- 전역 대기 8개·FIFO·취소·소스 격리·재시작 후 간격/429·아주 긴 대기 시간 보존.
- 예약 만료와 running 보류의 구분, SIGKILL 뒤 만료 시간이 지나도 새 DNS 없음.
- DB 대기 중 취소·다른 연결의 쓰기 잠금·시간 역행/변동·429/완료 저장 실패의 보수적 보류.
- redirect 간격·최종 DB 대기 뒤 정책 변경, 네트워크 중 개인 DB 작업 진행.
- 0016→0017·실패 롤백·기존 사용자 보존·검증된 백업/새 경로 복원·현재 제품 비활성.
- 운영 조회·정확한 token/기한/중지 확인/검토 시각·긴 cooldown·늦은 소유자 작업 거절.
- 과거 백업의 제한 재적용: `defer`는 대기를 더 길게만 바꾸고 running/다른 소스/개인 내용은 유지.

최종 `npm run check`의 strict 타입·프로덕션 빌드·**462개 Node 테스트**(조정 신규 17개 포함)가 통과했습니다. `search-desktop`, `search-mobile`, `recovery`의 **3개 Chromium 시나리오**도 통과했습니다. 브라우저 검증 뒤 추가한 운영 `defer`는 최종 전체 Node 검사에서 확인했으며 UI/전송 경로는 바꾸지 않았습니다. 기존 19개 브라우저 전체나 실제 모바일 기기의 검증으로 확대하지 않습니다.

기존 0001–0016 SQL 체크섬을 이전 보고서와 대조했습니다. 운영 DB/계정·기존 DB/백업을 변경하지 않고 모든 검증은 임시 자료로 수행했습니다. 의존성 추가·정책 변경·외부 요청·커밋/푸시는 없습니다. 기존 0016 대규모 카탈로그 성능은 당시 스키마의 결과이며 이번 전송 조정의 배포 처리량을 의미하지 않습니다.
