# 제목 분포와 페이지 경계별 검색 부하

이 문서의 최종 수치는 **0015·profile v1 당시 여섯 분포**의 기록입니다. 현재 0016의 offset 경로·마지막 페이지 소진 증명과 v2 재측정은 [후속 결과](CATALOG_OFFSET_SEARCH.md)를 따릅니다. 아래 전체 복귀 규칙과 큰 offset 미달 수치는 당시 동작입니다.

2026-10-25. [앞선 개선](CATALOG_SEARCH_OPTIMIZATION.md)의 반복 제목 분포 밖에서 검색 정확성과 DB 대기를 확인합니다. 모든 자료는 새 임시 DB에 적재하는 합성 자료이며 제품의 live 소스 gate는 그대로입니다.

## 재현 조건

```sh
npm run bench:concurrency -- --profile unique --output /tmp/loopshelf-unique.json
npm run bench:concurrency -- --profile boundary --output /tmp/loopshelf-boundary.json
```

v1의 `--profile`은 아래 여섯 이름이며 생략하면 기존 `repeated`입니다. 현재 v2는 실제 offset 끝에서 100곡/50곡 앞을 읽는 `offset-deep`도 받습니다. `boundary`는 제목 그룹이 최소 두 개 있어야 하므로 `--tracks 1`을 적재 전에 거절합니다. 한 번에 한 프로필만 실행합니다. 각 실행은 별도 임시 DB와 두 실제 로그인 세션을 만들고 종료/예외에서 제거합니다. 기존 DB 지정·인증 우회·제한 완화·실사이트 요청은 없습니다. 다른 벤치마크를 동시에 실행해 얻은 시간을 최종 측정과 섞지 않습니다.

| 프로필 | 합성 자료/검색 | 번갈아 읽는 두 페이지 |
| --- | --- | --- |
| `repeated` | 앨범마다 같은 제목 10종 | 첫 페이지 / 다음 커서 |
| `unique` | 곡마다 서로 다른 제목 10만 개 | 첫 페이지 / 다음 커서 |
| `sparse` | 뒤쪽 2% 앨범의 첫 곡만 `needle`, 기본 200곡 | 첫 페이지 / 다음 커서 |
| `blocked-prefix` | 출처/원본 키 순 앞 60% 앨범 차단, 현재 수록곡 4만 개 | 첫 페이지 / 다음 커서 |
| `boundary` | 반복 제목, 첫 제목 그룹 끝과 다음 제목 경계 | 끝에서 6곡 앞 / 다음 제목 시작 |
| `deep` | 반복 제목 | 전체 결과의 90% / 99% 위치 이후 |

각 프로필은 1만 앨범·10만 곡·내 자료 5천 개·다른 계정 자료 1천 개, 동시 1/4/8개, 여섯 종류의 요청마다 30표본·워밍업 2회입니다. 종류는 수록곡/앨범 검색, 개인 목록/메모 수정, 실제 세션 확인, 앨범 상세입니다. 한 프로필 540개 요청이며 실패/429/내용 불일치는 정상 성능 표본에 넣지 않고 실행을 실패시킵니다. 인증 세션 조회는 초기 두 번을 포함해 최대 98회로 기존 제한을 지킵니다.

`searchProfile`에 실제 일치 행 수·정규화 제목 수·차단 앨범 수·선택 위치·독립 결과/SQL 해시를 남깁니다. 제목 그룹 경계와 깊은 위치는 **이전 보고서의 전체 SQL**로 계산합니다. 측정할 코드를 정답으로 사용하지 않으며 준비 시간은 `profileSetupMs`로 분리합니다. 전체 기준 결과 중 선택한 두 페이지의 모든 DTO 필드·정렬·다음 커서/소진을 매 응답에서 대조합니다. 전체 10만 곡의 모든 페이지를 부하 측정했다고 주장하지 않습니다.

## 보조 후보 조회

고유 제목은 첫 제목 하나로 페이지를 채울 수 없고, 드문 제목/차단된 앞 출처/제목 경계에서도 기존 출처 후보가 부족할 수 있습니다. 전체 앨범의 메타데이터를 준비하기 전에 **전체 결과 정렬과 같은 순서의 곡 후보 최대 256개**를 추가로 확인합니다.

1. 기존 첫 제목/출처 후보가 `limit+1`개를 제공하면 그대로 사용합니다.
2. 그렇지 않으면 0014 제목 인덱스에서 제목 조건·출처 필터·현재 binding·출처 가용성·커서 정렬 조건으로 후보를 읽습니다. 제목이 바뀌어도 후보를 계속 읽으며 정렬은 정규화 제목 → 출처 → 원본 키 → 현재 위치 → Track UUID입니다.
3. 후보에 속한 앨범만 전체 메타데이터/근거 검사에 넣습니다. 합성 종류·앨범/곡 lifecycle·제거·현재 제목/채택 관찰·첫 origin 검사는 원래 조회와 공유합니다.
4. 전체 검사를 통과한 행이 `limit+1`개이면 그 앞 페이지와 다음 커서를 사용합니다. 앞선 모든 유효 행이 후보에 포함되어 있으므로 누락/순서 변경이 없습니다.
5. 부족하면 원래 전체 조회로 돌아갑니다. 후보 256개는 결과 상한이나 성공 0건 근거가 아닙니다. 처음 256개 후보의 앨범이 비활성인 사례도 전체 조회로 돌아가 뒤의 곡을 찾는지 검증합니다.

모든 단계는 같은 읽기 트랜잭션과 실제 세션 DB 경계 안에서 수행합니다. 기준 곡 변경 시 409, 현재 보관 정리, 개인 내용 비노출, 커서 조건은 그대로입니다. 새 인덱스/마이그레이션·결과 캐시·인증 변경은 없습니다. 큰 offset은 기존 전체 경로를 유지합니다. 이 보조 경로 역시 후보가 대부분 비가용인 모든 분포를 빠르게 만든다는 보장은 없습니다.

256은 이후 전체 근거를 검사할 후보의 수이며 SQL 전체 스캔 행 수의 상한이 아닙니다. 후보를 정렬할 때 같은 제목 그룹을 읽거나, 리터럴 부분 검색에서 불일치 제목을 지나갈 수 있습니다. 실제 제목 인덱스/현재 binding 탐색 계획과 그 비용은 원시 보고서에 포함합니다.

개선 전 [제목 경계 진단](evidence/2026-10-25-search-profile-boundary-diagnostic.json)의 동시 8개 전체 p95는 418.249ms였습니다. 고유 제목도 전체 조회로 돌아갔고, 제목 하나와 출처 앞부분만으로는 충분하지 않음을 확인했습니다. 진단 당시 일부 초기 검증 작업이 겹쳤으므로 통제된 성능 비율의 근거로 사용하지 않습니다. 위 표는 개선 후 최종 도구로 별도 실행한 결과이며, 서로 다른 분포를 하나의 전체 p95로 합치지 않습니다.

최종 strict 타입 검사·프로덕션 빌드·Node **438개**(신규 8개 포함)를 통과했습니다. 최초 실행에서 로컬 listener 제한으로 실행하지 못한 기존 HTTP 검사 5개도 listener를 허용한 전체 재실행에서 통과했습니다. 브라우저/순차 조회의 최종 검증은 아래에 별도로 기록합니다.

`tests/catalog-search-profiles.test.ts`는 100앨범/300곡에서 여섯 분포와 두 출처 필터를 모두 커서 순회해 독립 전체 SQL과 DTO를 대조합니다. 고유 제목의 앞 81앨범(243곡)이 비활성인 경우 후보 256개 중 정확히 13개가 남아 limit 12 페이지를 완성하고, 82앨범(246곡)이 비활성이면 전체 조회로 돌아가 뒤의 결과를 찾는지도 확인합니다. 개인 ID/내용/버전 보존, CLI의 실제 인증·전체 표본·임시 DB 정리·기존 DB 미접근도 검사합니다. 기존 280앨범 검사는 첫 후보/보조 후보/전체 복귀, Unicode 정규화와 반복 번호, 희소 제목·만료를 함께 확인합니다. 원래의 채택/삭제/제거/세션/커서 변경 테스트도 유지합니다.

제목/가용성 분포와 위치는 명시한 고정 사례입니다. 실제 카탈로그 분포·원격 HTTPS·TCP/브라우저·cold cache·다중 프로세스·대량 만료 정리·지속 유입·저사양 하드웨어의 성능 보장은 아닙니다. 기존 큰 offset 지연과 배포 수용량은 별도 미완료로 남깁니다.


## 기존 순차 조회와 화면 회귀

같은 합성 규모·M1 Ultra·예열 캐시에서 기존 `bench:catalog` 42개를 워밍업 3회/30표본으로 재실행했습니다. **41개만 p95 300ms 이내**이며 offset 99,900/limit 100은 **1,215.498ms**로 여전히 미달입니다. 보고서의 `passed: false`를 유지합니다. limit 100의 마지막 커서 페이지는 limit+1행을 확보하지 못해 추가 후보 조회 뒤 전체 조회로 돌아갑니다. 이 비용 때문에 `tracks-cursor-deep`는 111.962→146.735ms로 늘었습니다. 전체 성능이 일률적으로 좋아졌다고 주장하지 않으며, 이 마지막 페이지 비용도 후속 큰 offset 개선에서 다시 검토합니다. 위 여섯 혼합 부하의 limit 12/90%·99% 위치와 다른 조건입니다.

수록곡 검색·개인 카탈로그의 데스크톱/모바일과 실제 서버 백업/새 경로 복구 **5개 브라우저 시나리오를 재실행해 모두 통과**했습니다. 이전 전체 19개 중 이 5개를 재검증했으며 전체 19개 재실행으로 확대하지 않습니다. 운영 DB/계정·외부 소스·오디오·스키마·의존성·화면 변경은 없습니다.
