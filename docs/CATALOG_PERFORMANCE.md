# 합성 카탈로그 검색·탐색 성능

측정일: **2026-10-24**. 합성 **10,000개 앨범·100,000개 트랙**, 개인 저장 **5,000개**에서 21개 서비스 조회와 실제 로그인 세션을 사용하는 3개 Fastify 요청을 측정했습니다. 변경 전에도 모든 사례가 초기 p95 300ms 목표를 충족했고, 조회 범위를 줄인 후에도 모두 충족했습니다. 변경 후 가장 높은 p95는 **73.305ms**입니다. 이는 아래 한 대의 컴퓨터·데이터 분포·순차 요청 조건에 대한 결과입니다.

## 재현

프로젝트의 Node 버전과 lockfile 의존성을 사용합니다.

```sh
npm run bench:catalog -- --output /tmp/loopshelf-catalog-report.json
# 작은 실행 확인: 목표 규모의 성능 측정을 대신하지 않음
npm run bench:catalog -- --albums 20 --tracks 3 --samples 3 --output /tmp/loopshelf-catalog-smoke.json
```

기본값은 `--albums 10000 --tracks 10 --samples 30`입니다. 앨범 20–10,000, 앨범당 트랙 1–100, 표본 3–100을 받을 수 있습니다. `--output`을 생략하면 JSON을 stdout에, 진행 상황은 stderr에 출력합니다. 출력 파일은 새 경로여야 하며 기존 파일은 덮어쓰지 않습니다. `passed`는 해당 실행의 모든 p95가 300ms 이하인지를 나타내는 측정 결과입니다. 임계값 초과만으로 프로세스가 실패하지는 않습니다.

명령은 `.env`나 `DATABASE_PATH`를 사용하지 않고 OS 임시 디렉터리에 새 DB와 두 검증 계정을 만듭니다. 기존 DB를 지정하는 옵션은 없습니다. `CatalogStore.ingestSynthetic`과 개인 저장/출처 연결/JSON 서비스로 데이터를 만들고 실제 행 수·integrity·FK를 확인합니다. 끝나거나 오류가 나면 DB와 임시 디렉터리를 정리합니다. 음원·실사이트 요청·제품용 fixture 적재 경로는 없습니다. 강제 프로세스 종료 시 남은 OS 임시 파일은 별도 정리가 필요할 수 있습니다.

## 조건과 측정 범위

| 조건 | 값 |
| --- | --- |
| 컴퓨터 | Apple M1 Ultra, arm64, 논리 CPU 20개, 메모리 128 GiB |
| 운영체제 / 런타임 | Darwin 27.0.0, Node 24.21.0, SQLite 3.53.4 |
| DB | 디스크 파일, 약 232 MiB, WAL, synchronous FULL, page size 4096, cache_size -16000 |
| 데이터 | `catalog-scale-v1`, 두 소스 각 5,000앨범, 앨범당 10트랙, 반복 표시 번호 |
| 제목 | 한글·일본어·영어·전각 문자·리터럴 `%_`, 순번이 있는 합성 제목 |
| 개인 자료 | 현재 계정 4,900개 일반 저장 + 100개 원본 미연결, 추가 출처 100개; 다른 계정 1,000개 |
| 반복 | 사례별 첫 호출 별도 기록, 예열 3회 후 30회, 동시 요청 1개, nearest-rank p50/p95 |
| 통계 | 별도 ANALYZE/PRAGMA optimize를 실행하지 않은 새 DB |

서비스 시간은 쿼리 준비·읽기 트랜잭션·응답 객체 조립을 포함합니다. `withDatabase`를 확보한 뒤 타이머를 시작하므로 큐 대기 시간은 포함하지 않습니다. `authenticated-inject`는 실제 비밀번호 로그인 쿠키로 Fastify의 인증·직렬화까지 실행하지만 TCP·브라우저 렌더링은 포함하지 않습니다. 실행 계획 수집은 시간 측정 밖에서 실제 실행한 SQL과 바인딩 값으로 수행합니다. 보고서에는 SQL·계획·호출 수를 남기고 바인딩 값·계정 비밀값은 기록하지 않습니다.

같은 연결에서 적재 직후 측정하므로 OS 캐시가 예열된 조건입니다. `firstMs`도 cold-disk 지연을 뜻하지 않습니다. 비교 실행마다 같은 논리 데이터 분포를 새 DB에 만들며 UUID·생성 시각·물리 배치는 새로 생성됩니다. 원격 배포·실제 휴대전화·저사양 장치·동시 사용자/쓰기·큐 대기·cold cache·최대 길이 메모·정렬 편향·별칭/전체 트랙 검색·외부 소스 지연은 이번 결과에 포함하지 않습니다. 전체 10만 트랙 중 현재 앨범의 수록곡을 조회하며, 아직 없는 전역 트랙 검색 기능의 성능을 주장하지 않습니다.

## 조회 변경과 인덱스 판단

기존 `managedEntitySelect`는 단건의 현재 메타데이터·제거 보존용 응답을 만들기 위한 공통 projection입니다. 목록과 상세 수록곡까지 같은 JOIN을 재사용하면서 `SCAN e`와 정렬이 발생했습니다. 현재도 단건 응답 projection은 공유하지만, 목록 후보는 앨범 테이블에서 선택하고 상세 수록곡은 `catalog_album_state`의 현재 관찰 ID로 `catalog_track_binding(observation_id, position)`을 읽습니다. 상세에서 전체 Entity 탐색과 임시 정렬이 사라졌으며 같은 행의 표시 번호도 함께 읽습니다.

앨범 목록은 `album a CROSS JOIN entity e ON e.id=a.id`로 앨범을 Entity보다 먼저 읽습니다. 단순 INNER JOIN으로 바꾼 [첫 비교안](evidence/2026-10-24-catalog-first-candidate.json)은 통계 없는 DB에서 여전히 `SCAN e`를 선택해 앨범 조회가 더 느렸습니다. 최종 계획은 `SCAN a` 뒤 UUID 키 조회입니다. CROSS JOIN의 순서 고정은 [SQLite 공식 설명](https://sqlite.org/optoverview.html#manual_control_of_query_plans_using_cross_join)을 따릅니다. 데이터 분포나 SQLite 버전을 바꿀 때에는 이 결정과 통계 관리 방법도 다시 측정합니다.

새 FTS·메타데이터 복사본·인덱스·마이그레이션은 추가하지 않았습니다. 현재 1만 앨범/5천 개인 저장에서 목표를 충족하므로 별도 인덱스의 갱신/제거 동기화 비용을 추가할 근거가 없습니다. 앨범 정렬은 여전히 임시 B-tree를 사용합니다. 규모가 커지거나 대상 장치에서 목표를 벗어나면 정규화 제목 인덱스·검색 인덱스·페이지 전략을 재검토합니다. 현재 제목, NFKC 리터럴 검색, source/key/UUID 정렬, 현재 binding, 제거/차단·소유권 규칙을 유지합니다.

## 검증과 운영

`tests/catalog-performance.test.ts`의 3개 테스트는 전체 Entity 스캔·수록곡 임시 정렬 회귀, 제목 갱신·정렬·소유권·차단/제거·미연결 경계, 실제 CLI의 임시 DB 격리/정리와 실제 세션 측정 출력을 확인합니다. 시간 임계값은 일반 CI의 합격 조건으로 사용하지 않습니다. 작은 fixture 검증은 `npm run check`에 포함되고, 1만/10만 측정은 위 명령으로 별도 실행합니다. 기존 탐색·채택·개인 이식·인증 테스트도 함께 유지합니다.

최초 조회 개선 당시 스키마는 0010이며 해당 조회 변경에는 마이그레이션이 필요하지 않았습니다. 이후 보관/참조 스키마를 포함한 재측정은 아래에 별도로 기록합니다. 운영 DB와 계정은 변경하지 않았고 외부 자동 수집은 계속 `policy_disabled`입니다.

## 0012 보관 수명 추가 후 재측정

2026-10-24, 동일 Apple M1 Ultra/128 GiB, Node 24.21.0/SQLite 3.53.4에서 합성 **10,000 앨범·100,000 트랙·개인 저장 5,000개**의 24개 조회를 다시 실행했습니다. 동시성 1, ANALYZE 없음, 워밍업 3회·표본 30회, 동일 연결/따뜻한 OS 캐시, 네트워크와 브라우저는 제외한 조건입니다. 전부 p95 300ms 목표를 만족했고 가장 높은 p95는 깊은 앨범 페이지 **124.344ms**입니다. 개인 필터/페이지 p95는 **29.678ms**, 첫 개인 목록은 **3.224ms**, 앨범 수록곡은 **2.268ms**입니다. 이전 수치보다 모든 조회가 빨라졌다는 주장은 하지 않습니다. 새 종류/보관 상태 검사의 비용을 포함합니다.

```sh
npm run bench:catalog -- --output /tmp/catalog-retention.json
npm run bench:retention -- --output /tmp/catalog-retention-probe.json
```

[전체 조회 보고서](evidence/2026-10-24-catalog-retention.json)는 원시 표본·실제 실행 SQL/계획·스키마/코드 체크섬을 포함합니다. 기존 앨범 우선 조회와 관찰별 binding 인덱스는 유지합니다. 새 보관 검사에는 active lease만 담는 `(sample_kind, expires_at)` 부분 인덱스를 추가했습니다. 만료 후보를 검사하기 위해 모든 기존 fixture의 큰 JSON 행을 읽는 비용을 분리 측정한 뒤 적용했습니다.

[보관 검사 단독 보고서](evidence/2026-10-24-catalog-retention-probe.json)는 **단일 앨범·10개 트랙·10,000개 합성 과거 관찰(각 DTO에 트랙 10행)** 분포입니다. in-memory SQLite, 동시성 1, ANALYZE 없음, 3회 워밍업/30개 표본이며 실제 만료 쓰기·인증·네트워크 비용은 제외합니다. 같은 임시 DB에서 인덱스 유무를 비교합니다. 두 자료 분포를 전체 앨범 탐색/실제 사이트 성능으로 확대하지 않습니다.

| 보관 검사 분포 | 인덱스 없음 p50/p95(ms) | 인덱스 있음 p50/p95(ms) |
| --- | --- | --- |
| 기한 없는 기존 합성 관찰 10,000개 | 5.209 / 5.397 | 0.049 / 0.056 |
| 미래 기한의 합성 관찰 10,000개 | 5.808 / 5.981 | 0.050 / 0.077 |

재현 스크립트는 운영 DB/.env를 열지 않습니다. 실제 수명 만료의 대량 정리 지연, 허용된 live 관찰 분포, 여러 프로세스와 동시 사용자 부하는 아직 측정하지 않았습니다.


## 0013 개인 참조 종류 추가 후 재측정

2026-10-25(한국 시각), 최종 0013 스키마와 개인 DTO 종류 읽기를 포함해 같은 합성 **10,000 앨범·100,000 트랙·개인 저장 5,000개**에서 24개 조회를 측정했습니다. Apple M1 Ultra/128 GiB, Node 24.21.0/SQLite 3.53.4, 동시성 1, ANALYZE 없음, 같은 연결/따뜻한 OS 캐시, 워밍업 3회·표본 30회 조건입니다. 네트워크·브라우저·동시 대기는 포함하지 않습니다.

모든 조회가 p95 300ms 목표를 만족했습니다. 가장 높은 p95는 깊은 앨범 페이지 **133.317ms**, 앨범 수록곡은 **2.385ms**, 첫 개인 목록은 **3.535ms**, 개인 필터/페이지는 **37.441ms**입니다. 성능 개선 작업은 아니며 전 단계보다 일관되게 빨라졌다고 해석하지 않습니다. 실제 live 자료·대량 만료 쓰기·동시 사용자 성능은 검증 범위 밖입니다.

[최종 측정 보고서](evidence/2026-10-25-catalog-kinds-final.json)에 원시 표본·실행 계획·코드/마이그레이션 체크섬을 보관합니다. 0012까지의 SQL 체크섬은 이전 보관 수명 보고서와 동일하며, 앨범 우선 읽기와 관찰별 binding 인덱스를 유지합니다. 새 0013은 개인 참조 INSERT 검사용이며 읽기용 인덱스를 추가하지 않습니다. 같은 날의 [중간 보고서](evidence/2026-10-25-catalog-kinds.json)는 0013 추가 전 결과로 구분합니다.
