# 큰 offset 조회와 마지막 커서 페이지

2026-10-25. 합성 카탈로그의 기존 offset API에서 페이지 계약을 유지하면서 전체 근거를 반복 조합하는 비용을 줄입니다. 실제 소스 수집·live 저장·재생은 활성화하지 않습니다.

## 측정 후 선택한 구조

이전 `offset=99900&limit=100`의 서비스 p95는 1,215.498ms였습니다. 별도 임시 DB에서 기존 전체 SQL, 조인 순서, covering 인덱스, 가용성 집합, 첫 관찰 조회 분리, SQLite 캐시 확대와 현재 검색 순서의 파생 테이블을 비교했습니다. 모두 독립 이전 SQL의 결과와 대조하며 기존 DB를 열지 않습니다. `scripts/bench-catalog-offset-plans.ts`는 0015까지의 스키마를 사용해 당시 비교를 재현합니다. 이 SQL 실험은 인증·응답 조립을 제외한 예비 측정이며 제품 응답 시간으로 사용하지 않습니다.

0016의 `catalog_track_search_index`는 현재 공개 검색에 포함되는 **합성** 곡의 Track/Album/Source/관찰 UUID, 정규화 곡 제목, 출처/원본 키와 현재 binding 위치만 담습니다. 새 음악 정체성·개인 자료·원문 HTML·오디오를 만들지 않습니다. `catalog_track_search_order_idx`는 기존 제목 → source → 원본 키 → 현재 위치 → UUID 순서를 유지하고, 앨범별 인덱스는 영향받은 행의 정리에 사용합니다. FTS를 도입하지 않아 짧은 한일문·NFKC·리터럴 부분 검색의 의미는 같습니다.

양수 offset은 정렬 인덱스에서 limit+1개의 키를 먼저 선택하고 해당 앨범/곡의 현재 가용성·관찰·binding·첫 origin·제거 상태를 원본 테이블에서 다시 검사합니다. 두 읽기는 같은 동기 읽기 트랜잭션에 있으며 전후 정렬/관찰 fingerprint가 다르면 오류로 중단합니다. 짧은 성공·정상 0건으로 숨기지 않습니다. 페이지의 제목·길이·번호·URL·관찰 시각·검토 상태는 원본에서 읽습니다. 기존 인증·no-store·offset 상한·nextCursor 계약은 유지합니다.

## 동기화와 검증

`catalog_track_search_current` view가 기존 전체 SQL과 같은 검색 자격을 정의합니다. 0016은 현재 view로 초기 적재하며 SQLite AFTER trigger가 같은 쓰기 트랜잭션에서 해당 곡/앨범을 갱신합니다.

| 변경 | 검색 목록 처리 |
| --- | --- |
| 최초 저장, 현재 채택 관찰 변경, 현재 binding 추가/삭제 | 현재 목록으로 교체. 미채택 관찰은 새 순서로 사용하지 않음 |
| 곡 제목 변경, 트랙/앨범 lifecycle, 출처 가용성 | 정렬값 또는 포함 여부 반영 |
| 첫 origin 추가/삭제, 고정 자료 종류 | 근거를 갖춘 합성 자료만 포함 |
| 관찰 만료/정책 철회 정리, 콘텐츠 제거 | 검색 제목과 키도 목록에서 제거. 재생성으로 되살리지 않음 |
| 트랜잭션 실패 | 원본과 파생 목록을 함께 롤백 |

보관 기한/정책 정리는 시작·조회·기존 주기와 백업/복원 경계를 유지합니다. SQL trigger가 시간 경과만으로 실행되는 것은 아닙니다. identity·binding·관찰의 기존 불변 제약을 유지하며, 임의 SQL로 원본 관계나 trigger를 훼손하는 운영은 지원하지 않습니다.

앱 시작 시 정리 후, 검증된 백업/복원 시 `verifyCatalogSearchIndex`가 view와 저장 목록의 양방향 차집합을 검사합니다. 일치하지 않으면 시작/스냅샷 성공을 거절합니다. 페이지의 재검사는 선택된 행의 잘못된 근거를 잡지만 **인덱스에서만 빠진 모든 행을 매 요청마다 찾지는 않습니다**. 정상 쓰기의 trigger 동기화와 시작/스냅샷의 전수 비교가 그 경계를 담당합니다. 운영자가 직접 손상시킨 DB의 임의 조회 정확성을 보장하지 않습니다.

## 마지막 커서 페이지

offset 0/커서의 첫 제목·출처 후보 경로는 여전히 limit+1개의 적격 행을 확보해야 합니다. 보조 `ordered-window`는 전체 정렬 순서로 최대 256개의 **원시 후보**를 만든 뒤 전체 근거를 검사합니다. 이번 변경은 이 같은 CTE에서 원시 후보 수를 함께 읽습니다.

- 적격 limit+1행이 있으면 기존처럼 페이지를 사용합니다.
- 적격 행이 하나 이상이며 원시 후보 수가 **256 미만**이면 남은 후보를 전부 검사했으므로 짧은 마지막 페이지를 확정할 수 있습니다.
- 정확히 256개이거나 적격 행이 없어 카운터를 받지 못하면 기존 전체 조회로 돌아갑니다. 적격 행 수만으로 소진을 추측하지 않습니다.

257/256/255개 후보에서 앞선 156개가 부적격인 경우를 독립 전체 SQL과 대조합니다. 257번째 적격 행으로 다음 페이지가 생기는 경우를 누락하지 않으며, 카운터는 공개 DTO에 포함하지 않습니다. 기준 곡 재검사와 변경 시 409도 유지합니다.

## 운영과 복구

서버를 정상 종료하고 현재 코드의 검증된 백업을 만든 뒤 새 코드에서 `npm run db:migrate`를 실행합니다. 기존 0001–0015 SQL은 바꾸지 않습니다. 0016은 기존 UUID·관찰·개인 내용·수정 버전을 보존하고 파생 목록/인덱스/trigger만 추가합니다. 실패하면 배치와 이력을 함께 롤백합니다. 이전 코드로 돌아갈 때는 해당 버전의 백업을 **새 경로**에 복원합니다.

운영자 명령 `npm run catalog:reindex`는 현재 설정의 DB에서 보관 정리 후 파생 목록만 원자적으로 재생성하고 전수 비교합니다. 정상 종료 시 `indexedTracks` 수를 출력합니다. URL/제목으로 다른 항목을 합치거나 개인 ID/내용을 변경하지 않습니다. 서비스 재개 전 실행하는 유지보수 명령이며 HTTP로 노출하지 않습니다. 실패한 재생성은 파생 목록 교체를 롤백합니다. 그전에 수행한 정당한 보관 정리는 별도 트랜잭션입니다.

목록 불일치로 시작/백업이 거절되면 원본·마지막 정상 백업을 보존하고 서비스를 멈춘 상태에서 원인을 확인합니다. 정상 백업으로 새 경로 복원하거나, 손상이 이 파생 목록에만 한정된 것을 확인한 뒤 `catalog:reindex`와 검증된 새 백업을 수행합니다. 검증을 끄거나 이력을 삭제하지 않습니다. 전체 DB 손상은 이 명령의 복구 범위가 아닙니다. 정규화/Unicode 의미를 바꾸면 0014/0015 표현식 인덱스와 0016 파생 제목을 함께 갱신하는 새 마이그레이션 및 복원 검증이 필요합니다. [전체 운영 절차](OPERATIONS.md)

## 성능 검증 범위

기존 42개 순차 사례를 유지하고, 혼합 부하에는 `catalog-search-profiles-v2`의 `offset-deep`을 추가합니다. 이 프로필은 limit 100으로 끝에서 100곡/50곡 앞의 **실제 offset**을 번갈아 조회하며 독립 이전 SQL로 페이지·다음 페이지·개인 쓰기 결과를 비교합니다. 기존 커서 프로필을 offset으로 가장하지 않습니다.

최종 측정은 합성 1만 앨범·10만 곡, M1 Ultra·예열 캐시·단일 프로세스/연결에서 수행합니다. 원격 TCP/브라우저·cold cache·다중 프로세스·저사양 서버·대량 정리/지속 수집의 성능 보장은 아닙니다. 파생 목록은 읽기 비용을 줄이는 대신 저장 공간·갱신·시작/스냅샷 전수 검사 비용을 추가합니다. `bench:catalog`의 `seedMs`, `databaseBytes`, `maintenance`는 그 비용을 함께 기록하며 유지보수 시간은 한 번의 관찰값으로 p95가 아닙니다.

[12개 SQL 설계 비교 원시 자료](evidence/2026-10-25-offset-query-probe.json)의 예비 5표본 p95는 원래 조회 1,214.163ms, 가장 빠른 기존 조인/covering 조합 510.683ms, 64MiB 캐시 비교의 최저 622.767ms, 파생 순서 실험 11.512ms였습니다. 전부 같은 결과와 대조했습니다. 이 실험의 인덱스/캐시 확대는 제품에 적용하지 않았으며 최종 제품 수치는 위 30표본·원본 재검사 포함 결과입니다.

## 혼합 부하 최종 결과

같은 1만 앨범/10만 곡·두 실제 계정·한 프로세스/연결에서 동시 1/4/8개, 여섯 읽기/쓰기 종류마다 30표본·워밍업 2회로 실행했습니다. 최종 대규모 실행은 모두 순차적으로 수행했습니다. 네 프로필 × 세 동시성 × 여섯 종류의 **72조합 모두 p95 300ms 이내**, 총 **2,160개 정상 응답과 내용 검사**가 통과했습니다. 실패/429를 빠른 정상 표본으로 계산하지 않았습니다.

| 프로필 | 동시 1 전체 p95 ms | 동시 4 | 동시 8 | 해당 프로필에서 가장 높은 종류별 p95 |
| --- | ---: | ---: | ---: | ---: |
| [큰 offset: 99,900 / 99,950](evidence/2026-10-25-offset-deep.json) | 17.602 | 27.720 | 47.724 | 51.622 |
| [반복 제목: 첫/다음 페이지](evidence/2026-10-25-offset-repeated.json) | 7.072 | 16.321 | 28.386 | 38.668 |
| [제목 그룹 경계](evidence/2026-10-25-offset-boundary.json) | 79.675 | 89.641 | 173.407 | 181.544 |
| [90% / 99% 커서](evidence/2026-10-25-offset-cursor-deep.json) | 76.490 | 85.714 | 100.352 | 105.268 |

큰 offset 부하의 동시 8개 수록곡 요청 자체 p95는 45.873ms, DB 대기 29.248ms·점유 18.938ms입니다. 각 p95는 서로 다른 표본일 수 있어 합산하지 않습니다. offset 선택 페이지는 독립 전체 SQL/DTO와 대조하며 두 계정의 개인 수정·소유권·실제 세션 조건도 유지합니다. `byKind`, 시간 원시 표본, SQL 실행 계획, 최종 코드/스키마 해시는 각 보고서에 보존합니다.

이번 변경과 직접 관련된 네 프로필만 대규모로 재측정했습니다. 고유/희소/앞 60% 차단의 대규모 결과는 [0015의 여섯 분포 보고서](CATALOG_SEARCH_PROFILES.md)이며 0016의 일곱 프로필 전체 성능을 측정했다고 주장하지 않습니다. 일곱 분포의 소규모 정확성/CLI·정렬/차단/만료 회귀는 현재 코드로 통과했습니다. 조건별 시간 차이를 실제 외부 카탈로그 분포나 배포 수용량으로 일반화하지 않습니다.

재현 예:

```sh
npm run bench:catalog -- --samples 30 --output /tmp/loopshelf-offset-catalog.json
npm run bench:concurrency -- --profile offset-deep --samples 30 --output /tmp/loopshelf-offset-mixed.json
node scripts/bench-catalog-offset-plans.ts --albums 10000 --samples 5 --output /tmp/loopshelf-offset-sql.json
```

출력은 존재하지 않는 파일명을 사용합니다. 0015 SQL 설계 비교 명령은 예비 실험이며 현재 제품 성능은 앞의 두 명령으로 측정합니다.

## 자동 검증

신규 7개를 포함한 최종 strict 타입·프로덕션 빌드·전체 Node **445개**가 통과했습니다. `catalog-search-index.test.ts`는 0015→0016의 정확한 backfill·기존 내용 보존·실패 롤백·백업/새 경로 복원·개인 버전 보존·재채택·가용성·만료/제거·검색 목록 손상·원자적 재생성·실제 두 세션을 검사합니다. `catalog-offset-search.test.ts`는 257/256/255 원시 후보와 빈 결과의 소진 경계를 독립 SQL/DTO로 대조합니다. 기존 프로필 검증은 `offset-deep`을 포함한 일곱 가지의 전체 커서 순회를 유지합니다. 작은 벤치마크의 자체 출처 연결 충돌도 수정했으며 1만 앨범 기본 자료 배치는 바꾸지 않았습니다.
