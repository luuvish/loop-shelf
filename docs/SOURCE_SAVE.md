# 소스 앨범 저장의 입력·정책 계약

갱신일: **2026-10-25**. 상세 조회에서 개인 저장으로 넘어가기 위한 **별도 보관 정책·선택 사전 조건·내부 저장 흐름**을 구현했습니다. 현재 실제 자료의 보관 정책은 `unknown`이며 제품 진입점은 `policy_disabled`를 반환합니다. 정책을 허용으로 가정해도 live 저장 지원을 검증하기 전에는 `storage_unavailable`입니다. 실제 자료를 합성으로 바꾸어 기존 SQL에 넣지 않습니다.

원자적 카탈로그 적재·개인 저장은 **합성 자료와 실제 임시 로그인 세션으로만 검증**했습니다. HTTP 저장 endpoint·화면 버튼·백그라운드 작업은 추가하지 않았습니다. 기존 검색/상세 조회는 계속 읽기 전용이며 공용 UUID나 개인 저장을 자동 생성하지 않습니다.

## 입력과 선택 조건

내부 `save(input, headers, signal?)` 입력은 다음 필드만 허용합니다.

| 필드 | 의미 |
| --- | --- |
| `sourceId`, `externalKey` | 사용자가 명시적으로 선택한 고정 소스의 앨범 키. 기존 상세 입력 검사를 그대로 사용 |
| `expectedFingerprint` | 사용자가 확인한 정확한 상세 관찰에 대한 64자리 SHA-256 사전 조건 |
| `titleOverride` | 직접 작성한 개인 제목, 기본 null, 1–300자 |
| `note`, `favorite` | 개인 메모(최대 10,000자)·즐겨찾기. 기본 빈 문자열/false |

입력 전체는 UTF-8 32 KiB 이하이며 알 수 없는 필드는 거절합니다. `userId`, 세션 ID, URL, Entity UUID, 자료 종류, 허가 여부, 원문/상세 DTO를 본문으로 받지 않습니다. userId는 실제 쿠키 세션에서만 얻습니다. 헤더와 입력은 첫 비동기 대기 전에 복사하여 대기 중 호출자 변경이 저장 내용·소유자를 바꾸지 못하게 합니다.

`sourceDetailFingerprint`는 공통 DTO 검사 후 상세 내용·취득 시각/파서 버전/원문 해시/자료 종류/출처 URL·경고를 해시합니다. parsedAt만 바뀐 동일 관찰의 재파싱은 허용하고 캐시 전달 방식은 해시에 넣지 않습니다. 이것은 음악 식별자나 접근 토큰이 아니며, 알고 있다는 이유로 적재/조회/저장 권한이 생기지 않습니다. 현재 상세 HTTP 응답에 이 값을 추가하지 않았습니다. 후속 저장 API/UI에서는 사용자가 확인한 상세의 사전 조건을 제공하고 변경 시 재선택을 요구해야 합니다.

처음에는 **앨범 저장만** 대상으로 합니다. 키 없는 수록 위치를 곧바로 저장할 트랙 ID로 받아들이지 않습니다. 신규 앨범의 첫 목록에 UUID를 할당하고, 기존 목록 변경은 [카탈로그 관찰/채택 규칙](CATALOG.md)에 따라 검토 상태로 남깁니다. 트랙 저장은 채택한 현재 Track UUID를 사용하는 기존 개인 API의 범위입니다.

## 보관 정책과 수명

`CatalogAdmissionPolicy`는 소스·자료 종류, 자체 revision, 메타데이터 정책 revision, 현재 파서 버전과 별도의 `persistence` 판단을 가집니다. 캐시/표시가 허용돼도 카탈로그 보관 허용을 추론하지 않습니다.

- `unknown`과 `denied`는 모두 저장을 거절합니다. 제품의 `catalogAdmissionPolicy`는 코드에서 고정된 unknown 상태이며 HTTP/환경 변수로 열 수 없습니다.
- allowed에는 검토 시각·비어 있지 않은 근거 목록·양의 정수 보관 한도가 필요합니다. 미래 검토일·누락된 근거·잘못된 한도를 거절합니다. 현재 상한은 Adapter 앨범 캐시와 같은 30일이며 이는 소스의 공식 허용 기간을 뜻하지 않습니다. 실제 활성화 시 검토된 기간이 더 짧으면 그 값을 사용해야 합니다.
- fresh 상세 성공만 저장 후보로 받습니다. stale·갱신 실패·부분/시간 제한 응답·미지원/실패·빈/잘못된 수록곡·선택한 소스와 불일치한 응답은 저장하지 않습니다. 캐시/표시 허용이 필요하며 transport 응답에는 수집 허용도 필요합니다.
- 취득 ≤ 파싱 ≤ 현재 시각을 확인하고, 현재 파서/정책 버전 및 선택 fingerprint를 비교합니다. `min(원래 expiresAt, capturedAt + 보관 한도)`가 저장 후보의 한계입니다. 재시도·캐시 적중·개인 저장 시점부터 보관 기한을 다시 시작하지 않습니다.
- 초기 정책과 최종 정책 전체를 비교합니다. revision만 유지한 채 판단/근거/한도가 바뀐 경우에도 저장을 거절합니다. DB 최종 인증 대기 중 만료·철회·콘텐츠 제거도 다시 확인합니다.

**승인 수명은 관찰과 함께 영속화합니다.** `admitSourceAlbum`이 반환한 policyRevision/retainUntil을 `ingestRetainedAlbumInTransaction`으로 전달하며 기존 관찰의 재시도로 기한을 바꾸지 않습니다. 개인 쓰기와 최종 검사 실패는 수명 기록까지 함께 롤백합니다. 기존 unleased 합성 fixture 경로는 별도로 유지합니다. live 요청은 고정 제품 정책을 독립적으로 검사하고 제품 저장 guard도 닫혀 있습니다. [상세 계약](CATALOG_KINDS.md)

## 인증과 원자적 저장

제품 진입점 `src/source-save.ts`는 실제 서버 Better Auth 인스턴스, 제품 상세 서비스, 고정 보관 정책과 live 모드를 결합합니다. 내부 `source-save/service.ts`의 의존성 구성은 오프라인 검증용입니다. HTTP/환경 변수에 주입 경로를 두지 않으며, 쓰기 구현을 교체하는 callback도 받지 않습니다.

1. 실제 쿠키 세션을 읽고 필수 `X-LoopShelf-Session`과 비교합니다. 본문으로 소유자를 지정하지 않습니다.
2. 보관 정책·자료 종류·저장소 지원 여부·제거 상태를 검사합니다. 제품은 이 지점에서 비활성으로 종료하므로 소스 요청이나 적재를 시작하지 않습니다.
3. 합성 검증 모드에서는 DB 경계를 해제한 뒤 선택한 키로 상세 서비스에 요청합니다. 브라우저가 보낸 메타데이터는 사용하지 않습니다.
4. 같은 DB 경계 안에서 실제 세션을 다시 검사하고 초기 사용자/세션과 비교합니다. 다른 로그인이 생겼다는 이유만으로 기존 유효 세션을 폐기된 것으로 간주하지 않습니다. 쿠키를 바꾼 새 요청의 세션 사전 조건도 일치해야 합니다.
5. 최종 상세 `recheck`와 보관 정책·선택 내용·기한·제거 검사를 수행합니다. 이후 짧은 동기 immediate 트랜잭션에서 공용 관찰/Entity와 개인 저장을 함께 반영합니다. Promise나 네트워크를 트랜잭션 안에서 기다리지 않습니다.
6. 쓰기 직후 commit 전에도 취소/시간·정책·제거·수명 검사를 수행합니다. 개인 쓰기 실패나 마지막 확인 실패 시 새 UUID/관찰/제목 변경/개인 행을 **모두 롤백**합니다.

전체 대기는 초기/최종 인증과 DB 큐를 포함하여 12초, 동시 작업은 서비스 인스턴스당 16개입니다. 대기 중 취소/timeout이 반환된 뒤 큐가 풀려도 다시 검사하므로 늦은 쓰기가 발생하지 않습니다. 동기 SQLite 실행 자체를 강제 중단하는 보장은 아닙니다. 운영 HTTP의 Origin·body limit·분당 제한·서버 종료 취소와 클라이언트의 현재 쿠키 재확인은 후속 API 연결 때 별도로 적용해야 합니다. 현재 검색/상세 HTTP 한도를 변경하지 않았습니다.

## ID·재시도·실패

`CatalogStore.ingestRetainedAlbumInTransaction`은 호출자가 `withDatabase`와 동기 트랜잭션을 소유할 때만 사용하는 내부 앨범 진입점입니다. 단독 트랜잭션 밖 호출과 유효하지 않은 수명을 거절하고 live 입력에는 고정 제품 정책을 별도로 확인합니다. 기존 `ingestSynthetic`과 `ingestSyntheticInTransaction`의 합성 전용 계약은 유지합니다.

동일 소스 키는 같은 Album/SourceEntity, 동일 관찰은 같은 observation UUID를 재사용합니다. 다른 소스/키를 제목으로 합치지 않습니다. 저장된 공용 상세가 선택한 상세보다 최신이면 과거 응답으로 새 관찰·저장을 만들지 않고 `snapshot_changed`로 재선택을 요구합니다. 변경된 키 없는 수록곡은 기존 Track/개인 저장 ID를 보존하며 `review_required`를 반환합니다. 검색 표시명으로 상세 제목을 덮어쓰지 않습니다.

개인 저장은 기존 `CatalogLibraryStore.create`를 사용합니다. 같은 계정/Entity의 재요청은 기존 개인 ID·제목 override·메모·즐겨찾기·버전을 반환하며 새 기본값으로 덮어쓰지 않습니다. 다른 계정은 같은 공용 앨범에 독립된 개인 ID를 가집니다. null 제목은 현재 공용 제목으로 계산하고 출처 제목을 개인 필드에 복사하지 않습니다. 기존 원본 미연결 행은 자동 연결하지 않습니다.

이 단계는 별도의 요청 UUID 영수증을 추가하지 않았습니다. 재시도 때도 인증·정책·관찰을 다시 확인하며 자동 재전송은 없습니다. 기존 개인 저장을 명시적으로 삭제한 뒤 다시 저장하는 것은 새로운 개인 저장입니다. 후속 UI는 응답 유실 후 최신 선반/관찰을 확인하고 사용자가 명시적으로 재선택하게 해야 합니다.

실패는 인증/세션 조건, 입력, 정책/버전/관찰 변경, 만료/재조회 필요, 제거/카탈로그 불가, 취소/시간 제한/대기 초과와 소스/DB 실패를 구분합니다. 실패 결과에 보유 메타데이터나 다른 계정의 개인 내용을 붙이지 않습니다. 제거 영수증이 있는 소스는 재적재/중복 저장으로 되살리지 않으며 기존 개인 내용은 [제거 계약](CATALOG_REMOVAL.md)에 따라 보존합니다.

원자적 롤백 범위는 카탈로그 관찰/Entity·개인 저장입니다. 상세 서비스가 먼저 갱신하거나 정책에 따라 지운 메타데이터 캐시는 별도의 [Adapter 수명 계약](SOURCE_ADAPTERS.md)을 따르며 이 개인 저장 트랜잭션의 일부가 아닙니다.

## 검증과 남은 범위

`tests/source-save.test.ts`의 **30개 테스트**는 임시 SQLite·합성 상세·실제 Better Auth 쿠키 세션을 사용합니다. 제품 비활성/live 저장 거절, 엄격한 입력/선택 조건, 캐시와 별도 보관 허용/수명, 두 계정·동시 저장·중복 내용 보존, 수록곡 검토 보류, 최신 관찰 보호, 신규/기존 카탈로그 변경의 롤백, 조회 중 제거·실제 로그아웃/세션 만료/비밀번호 재설정·정책 철회, 초기/최종 인증/DB/소스 대기 제한·취소 뒤 늦은 쓰기 차단을 검사합니다. 외부 요청이나 운영 DB/계정 변경은 없습니다.

최초 내부 서비스 검증은 Node 332개·브라우저 15개였습니다. 승인 수명 영속화/재시도, 만료된 같은 곡 목록의 검토 유지, JSON으로 외부 정보/기한을 복원하지 못하는 3개를 추가했습니다. 2026-10-25의 최종 검증은 strict 타입 검사·프로덕션 빌드·전체 **361개 Node 테스트**와 **15개 Playwright 시나리오**를 통과했습니다. 이번 스키마/개인 화면 변경의 범위는 [자료 종류·JSON v2 계약](CATALOG_KINDS.md)에 기록합니다.

0012 [보관 수명 모델](CATALOG_RETENTION.md)에 이어 [개인 DTO/JSON v2와 내부 승인 수명 연결](CATALOG_KINDS.md)을 구현했습니다. 다음은 선택 fingerprint/저장 사전확인과 실제 세션 저장 HTTP API입니다. 제품 live guard는 여전히 닫혀 있으며 사이트 정책·공용 live 경계·실사이트 검증을 완료한 뒤에만 활성화할 수 있습니다.
