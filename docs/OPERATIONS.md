# LoopShelf 실행·업그레이드·백업·복구

검증일: **2026-10-22**. 현재 개인 북마크 앱을 로컬 영속 디스크의 단일 서버에서 운영하는 절차입니다. Node **24.21.0**, SQLite **3.53.4**, macOS의 loopback HTTP와 Playwright Chromium으로 확인했습니다. 원격 HTTPS·역방향 프록시·다중 서버 배포는 아직 검증하지 않았습니다.

## 최초 실행

저장소 루트에서 `.node-version`에 맞는 Node를 사용합니다. 기존 `.env`가 있으면 그대로 유지합니다.

```sh
npm ci --ignore-scripts
test -e .env || cp .env.example .env
chmod 600 .env
node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"
```

생성한 값을 `.env`의 `BETTER_AUTH_SECRET`에 넣습니다. `DATABASE_PATH`는 `.local/loopshelf.sqlite`, `APP_ORIGIN`은 `http://127.0.0.1:3000`, `PORT`는 `3000`이 기본값입니다. 환경변수가 `.env`보다 우선하므로 다른 DB 경로가 export되어 있지 않은지 확인합니다. 계정·비밀값은 자동 생성되지 않습니다.

```sh
npm run check
npm run db:migrate
npm run account:create -- --email you@example.com --name 'Your name'
npm start
```

`check`는 strict 타입 검사·프로덕션 빌드·Node 테스트를 포함합니다. 계정 명령에서 12–128자 비밀번호를 숨겨 입력합니다. [앱 열기](http://127.0.0.1:3000)에서 로그인하고 직접 URL 북마크를 저장해 봅니다. 개발은 `npm run dev`로 실행하며 Service Worker를 사용하지 않습니다.

서버는 127.0.0.1에 바인딩하고 Host를 검사하므로 주소의 `localhost`/`127.0.0.1`을 섞지 않습니다. `APP_ORIGIN`만 바꿔 LAN/인터넷에 공개할 수는 없습니다. 환경·계정·API의 세부 계약은 [BACKEND.md](BACKEND.md)를 참고합니다.

## 백업

```sh
npm run db:backup -- --output .local/backups/manual-20261022.sqlite
```

매번 다른 출력 파일명을 사용합니다. `Backup verified.`와 종료 코드 0을 확인합니다. 이 명령은 실행 중인 DB에서도 SQLite 온라인 백업으로 커밋된 WAL 데이터를 포함하며, 독립된 DELETE journal 스냅샷의 integrity/FK 검사를 마친 뒤 성공합니다. 출력은 0600, 새 디렉터리는 0700이고 기존 파일을 덮어쓰지 않습니다. 실행 중인 `.sqlite` 파일만 `cp`하는 방식은 이 절차를 대체하지 않습니다.

DB 백업에는 모든 계정의 비밀번호 해시·세션·개인 북마크·메모가 포함됩니다. 접근을 제한하고, 필요한 보관 기간과 별도 저장 장치 복사 정책을 운영자가 정합니다. `.local`의 백업만으로 같은 디스크의 고장까지 복구할 수는 없습니다. 사용한 코드 버전·`package-lock.json`·Node 버전·설정과 비밀값도 별도로 보관해야 합니다. JSON 내보내기는 한 사용자의 북마크 이식용이며 전체 DB 백업을 대체하지 않습니다.

합성 카탈로그와 그 개인 저장 UUID·제목·메모·즐겨찾기·SourceEntity 연결, 원본 미연결 개인 항목도 전체 DB 백업에 포함합니다. 북마크 JSON과 별도의 카탈로그 JSON은 개인 자료의 이식이며 인증·공용 음악 메타데이터·운영 제거 결정을 포함한 설치 전체 백업을 대신하지 않습니다. [범위와 검증](CATALOG_LIBRARY.md)

## 업그레이드

1. 실행 중인 서버를 Ctrl-C/SIGTERM으로 정상 종료합니다. 현재 코드와 DB 경로를 기록하고 **현재 코드에서** 위 백업 명령을 실행합니다.
2. 선택한 새 코드와 lockfile을 준비하고 `npm ci --ignore-scripts`, `npm run check`를 수행합니다.
3. 같은 DB 경로와 설정으로 `npm run db:migrate`를 실행합니다. 기존 DB에 미적용 변경이 있으면 `<DATABASE_PATH>.backups/`에 검증된 백업을 만든 후 배치 전체를 한 트랜잭션으로 적용합니다. 실패하면 배치 전체를 롤백합니다.
4. `npm start` 후 아래 조회·수정 확인을 수행합니다. 일반적인 서버 재시작은 유효한 세션을 유지합니다.

현재 최신 스키마는 `0017_source_request_coordination.sql`입니다. 적용한 SQL의 체크섬·이력 불일치는 자동 수정하지 않습니다. 실패하면 실행을 중단하고 해당 DB 이력과 일치하는 코드를 확인합니다. 이전 코드로 돌아가려면 그 코드에 맞는 백업도 함께 새 경로에 복원합니다. 업그레이드된 DB에 이전 SQL을 역으로 적용하는 명령은 없습니다.

## 새 DB 경로로 복구

서버를 정상 종료한 상태에서 수행합니다. 원본 DB와 백업은 보관하고, 복원 대상은 존재하지 않는 파일명을 선택합니다.

```sh
npm run db:restore -- --input .local/backups/manual-20261022.sqlite --output .local/loopshelf-restored-20261022.sqlite
```

`Restore verified`와 종료 코드 0을 확인합니다. 원본 스냅샷은 변경하지 않으며 복원본에만 다음 처리를 적용합니다.

- 북마크·Entity·LibraryItem의 UUID, 사용자별 소유권, 제목·메모·즐겨찾기·출처 연결을 백업 시점으로 되돌립니다. 백업 이후의 추가·수정·삭제는 복원본에 포함되지 않습니다.
- 모든 로그인 세션과 임시 인증 토큰을 제거합니다. 세션에 묶인 60초 삭제 복구 영수증도 FK cascade로 제거합니다. 백업 이후 로그아웃한 세션이 되살아나는 것을 방지합니다.
- integrity/FK 검사에 실패하면 성공을 보고하지 않습니다. 복원본 준비 중 오류가 나면 불완전한 출력 파일을 제거합니다. 기존 출력 파일·원본은 덮어쓰지 않습니다.

`.env`의 `DATABASE_PATH`를 방금 만든 파일로 바꾸고 기존 앱 origin·비밀값을 유지합니다. 서버를 다시 시작하기 전에 **새 경로가 적용되는 환경에서** 실행합니다.

```sh
npm run db:migrate
```

같은 스키마이면 migration은 변경 없이 검사만 수행합니다. 오래된 백업이면 현재 코드가 아는 마이그레이션을 명시적으로 적용하며, 적용 전에 자동 백업합니다. 더 새로운 버전이거나 이력이 다른 백업은 일치하는 코드를 먼저 준비합니다.

**카탈로그 제거 결정을 서버 재개 전에 재적용합니다.** 제거 후 백업은 `catalog_removal`을 유지하지만 제거 전 백업에는 이후 결정이 없습니다. 별도로 보관한 제거 영수증의 sourceEntityId/사유로 `npm run catalog:remove -- --source-entity-id '<SOURCE_ENTITY_UUID>' --reason rights_request`를 복원본에 실행하고 제거 상태를 확인합니다. restore 명령이 과거 백업에 이후 제거 이력을 자동 합치지는 않습니다. `not_found`/충돌은 성공으로 간주하지 말고 대상과 근거를 확인합니다. 기존 백업·미사용 페이지·WAL의 물리적 소거는 별도 보관/폐기 범위입니다. [제거 명령과 보존 범위](CATALOG_REMOVAL.md)

확인이 끝나면 `npm start`로 서버를 시작합니다.

**복구 후에는 모든 사용자가 다시 로그인해야 합니다.** 이미 열려 있던 창은 재접속 시 세션을 확인하고 개인 화면과 미저장 초안을 제거합니다. 다른 창에서 다시 로그인하더라도 이전 `X-LoopShelf-Session`의 쓰기는 거절합니다. 오프라인 새 창은 미리 준비된 정적 앱 셸의 연결 안내만 보여주고 개인 자료는 제공하지 않습니다.

계정과 비밀번호 해시도 백업 시점의 값입니다. 백업 이후 생성한 계정·비밀번호 변경·계정 상태 변경은 별도로 재적용해야 합니다. 필요한 경우 새 DB 경로로 `npm run account:reset-password -- --email you@example.com`을 실행한 뒤 서비스를 재개합니다. 세션 제거만으로 백업 이후의 계정 변경까지 복구되지는 않습니다.

## 복구 완료 확인

1. `/api/health`가 `{"status":"ok"}`를 반환하는지 확인합니다. 이것만으로 개인 데이터 복구가 검증되지는 않습니다.
2. 브라우저에서 다시 로그인하고 백업 시점의 대표 북마크·메모·즐겨찾기·연결된 원래 출처를 확인합니다. 연결된 출처 제목/메모의 검색도 확인합니다.
3. 메모를 수정하고 새로고침해 유지되는지 확인합니다. 여러 계정을 운영한다면 각 계정이 자신의 자료만 볼 수 있는지도 확인합니다.
4. PWA 창에서 서버에 재접속해 로그인·조회가 되는지 확인합니다. 셸 업데이트 대기가 표시되면 LoopShelf의 기존 창을 모두 닫고 다시 엽니다. [PWA 동작](PWA.md)

문제가 있으면 서버를 멈추고 보관한 이전 코드·원래 DB 경로로 돌아갑니다. 이미 복원본에 새로 저장한 내용은 원본 DB로 자동 합쳐지지 않습니다. 먼저 두 DB를 각각 보관하고 사용자 JSON 이식의 충돌 검사를 사용해 필요한 내용을 검토합니다. 두 DB에 동시에 쓰는 서버를 실행하지 않습니다.

## 자동 검증 근거와 한계

```sh
npx playwright install chromium
npm run test:e2e
```

복구 시나리오만 재현하려면 `npm run build` 후 `npx playwright test --project=recovery`를 실행합니다. [테스트](../tests/browser/recovery.spec.ts)는 `.env`를 읽지 않는 명시적 임시 환경에서 실제 계정 CLI와 `src/server/main.ts` 프로세스를 실행합니다. 예약 포트 4187–4190은 비어 있어야 합니다. 실제 운영 DB·계정은 사용하지 않습니다.

검증 내용: 실행 중 온라인 백업 → 백업 이후 변경 → 서버 정상 종료 → 새 경로 복원 → 서버 재실행 → 백업에 있던 두 세션의 401 확인 → PWA 재접속·재로그인 → UUID·원래 내용·출처 연결 일치 → 검색·브라우저 수정·새로고침 → 다른 계정의 조회/수정 거절. 원본 DB의 백업 이후 변경과 백업 파일의 SHA-256이 그대로인 것도 확인합니다. Node 테스트는 실패 시 출력 정리, 이전 스키마 복원·업그레이드, 세션/임시 인증 정보 제거, 트랜잭션·권한·API도 검증합니다.

브라우저 복구는 개인 북마크 범위입니다. 별도 Node 테스트에서 합성 카탈로그의 콘텐츠 제거와 제거 후 백업 복원·재적재 거절도 확인했습니다. 전원 차단/디스크 고장 실험, 백업 주기 자동화, 복구 시간·유실 허용량 보장, 운영 환경의 동시 부하, 실제 휴대전화·Safari, 원격 배포는 검증하지 않았습니다. 합성 1만 앨범·10만 트랙의 순차 조회 성능은 [전용 임시 DB 측정](CATALOG_PERFORMANCE.md)으로 확인했습니다. 외부 카탈로그 수집·스트리밍·플레이리스트·청취 이력도 아직 제공하지 않습니다.

## 보관 기한 재검사

0012 보관 모델은 앱 시작/10초 정리와 카탈로그 읽기 전에 만료·현재 보관 정책을 확인합니다. online backup 및 새 경로 restore도 생성한 복사본에서 검사하며 원본/과거 백업은 수정하지 않습니다. 공유·수동 근거가 있으면 정리와 해당 읽기를 중단하므로 `removal_conflict`의 근거를 검토해야 합니다. 자동으로 개인 제목/메모를 지우거나 제약을 해제하지 않습니다. 기한 검사는 백업 이후의 영구 제거 결정 재적용을 대신하지 않습니다. 과거 백업 파일 자체의 보관/폐기와 물리적 소거는 별도 운영 절차입니다. [보관·복원 계약](CATALOG_RETENTION.md)

0013은 기존 v1 개인 JSON 참조를 다시 쓰지 않고 새 참조의 명시적 자료 종류·같은 종류의 출처 연결을 검사합니다. 이전 앱은 새 스키마 이력 때문에 시작이 거절됩니다. 스키마 기록을 지워 이전 코드로 열지 말고, 이전 코드로 되돌릴 때는 해당 버전의 백업을 새 경로에 복원합니다. [v1/v2 호환과 버전 경계](CATALOG_KINDS.md)

## 0014 수록곡 검색 인덱스 업그레이드

업그레이드 전 동일 버전 코드로 백업하고, 새 코드에서 `npm run db:migrate`를 실행한 뒤 앱을 시작합니다. 0014는 곡 제목의 파생 검색 인덱스만 추가하며 기존 개인/공용 ID와 내용은 유지합니다. 이미 적용한 0001–0013 SQL을 수정하지 않습니다. 실패한 배치는 인덱스·마이그레이션 이력을 함께 롤백하며 이전 앱은 새 이력의 DB로 시작하지 않습니다.

검색 인덱스는 `normalize_search`에 의존합니다. 새 코드는 일반 DB와 백업 복사본·읽기 전용 복원 원본에도 같은 함수를 등록합니다. 정규화 의미나 Node/Unicode 동작이 바뀌면 새 마이그레이션을 통한 인덱스 재생성과 검색/백업/복원 검증을 검토해야 합니다. 복원은 여전히 새 경로만 허용하며 세션/임시 토큰을 제거합니다. 외부 콘텐츠 제거 결정 재적용도 기존 절차를 따릅니다. [계약과 검증](CATALOG_TRACK_SEARCH.md)


## 0015 앨범 검색 인덱스 업그레이드

동일 버전 코드로 백업한 뒤 새 코드의 `npm run db:migrate`를 실행합니다. 0015는 현재 앨범의 정규화 제목 인덱스만 추가하며 기존 UUID·개인 내용·관찰·버전은 유지합니다. 0001–0014 SQL을 수정하지 않습니다. 업그레이드/실패 롤백·제목 갱신/제거·검증된 백업/새 경로 복원을 확인했습니다. 이전 코드로 되돌릴 때는 해당 버전의 백업도 새 경로에 복원합니다. 정규화 함수/Unicode 규칙을 바꾸면 0014/0015 제목 인덱스 재생성을 검토합니다. ## 0016 현재 수록곡 검색 목록

기존 0001–0015 SQL은 그대로 두고 `db:migrate`로 현재 공개 검색 순서의 파생 테이블·인덱스·동기화 trigger를 추가합니다. UUID·관찰·개인 메모·수정 버전은 유지합니다. 앱 시작과 백업/복원은 현재 원본 view와 목록을 전수 비교하며 불일치 시 성공을 거절합니다. 이전 스키마 스냅샷은 원래 절차로 새 경로 복원 후 업그레이드합니다.

`npm run catalog:reindex`는 서버가 중지된 유지보수 시간에 현재 DB의 보관 정리와 파생 목록 재생성/검증을 수행합니다. 출력은 `indexedTracks`이며 개인 데이터나 원본 UUID를 재발급하지 않습니다. 정상적인 사용에서 매번 실행할 필요는 없습니다. 목록 불일치로 백업도 거절된 경우 검증을 끄지 말고 원본/마지막 정상 백업을 보존한 뒤 손상이 파생 목록에만 한정된 것인지 확인합니다. 정상 백업의 새 경로 복원 또는 목록 재생성 후 검증된 새 백업·앱 시작을 수행합니다. 전체 DB 손상이나 이후 콘텐츠 제거 결정을 대신 복구하지 않습니다. 정규화 규칙 변경은 0014/0015와 0016을 함께 재생성하는 새 마이그레이션으로 처리합니다. ## 0017 소스 요청 상태와 중단 복구

업그레이드 전 기존 코드의 검증된 백업을 만들고 `db:migrate`로 운영 상태 테이블/인덱스를 추가합니다. 기존 UUID·개인 내용·0001–0016 SQL은 유지합니다. 같은 로컬 DB의 프로세스가 소스별 요청 간격·429 대기·예약을 공유합니다. 이번 검증은 합성 응답만 사용했으며 실제 수집 정책은 비활성입니다.

`npm run source:requests -- inspect --source zophar`로 source 상태와 예약 token/owner/기한/단계만 조회합니다. 기한이 지난 `running`도 자동으로 지우지 않습니다. 모든 worker를 중지하고 실제 요청 종료·소스의 대기 요구를 검토한 뒤에만 `recover --source … --token … --reviewed-retry-at … --confirm-workers-stopped`를 실행합니다. 정확히 일치하는 만료된 running token만 해제하며 검토 시각은 최소 현재+60초, 기존 더 긴 대기는 보존합니다. 플래그는 운영자 확인이며 worker 중지를 자동 탐지하는 기능이 아닙니다. [정확한 명령·실패/시계 경계](SOURCE_COORDINATION.md)

백업과 새 경로 복원은 소스 대기·running 보류도 보존합니다. 세션 제거와 함께 초기화하지 않습니다. 과거 백업에는 이후 429/시도가 없으므로 복원 전 최신 상태를 별도로 보존·대조하고, 알려진 더 긴 제한과 종료 불확실성을 서비스 재개 전에 검토해야 합니다. `source:requests defer --source … --reviewed-retry-at … --confirm-workers-stopped`는 예약을 지우지 않고 기존보다 긴 대기만 적용합니다. DB 복사본 둘을 동시에 활성화하면 공통 제한이 되지 않습니다. 다른 호스트/네트워크 파일시스템·서로 다른 설치의 공통 quota와 시계 교정 중 정확한 경과 시간은 보장하지 않습니다. 검토 전 외부 수집 활성화나 상태 직접 삭제로 제한을 우회하지 않습니다.
