# 카탈로그 개인 자료 JSON 이식

갱신일: **2026-10-25**. 합성 자료와 외부 자료 참조에 저장한 개인 항목·앨범 출처 판단을 계정별로 내보내고 복원합니다. 공용 음악 메타데이터를 이식하거나 새로 수집하지 않습니다. 기존 [직접 입력 북마크 JSON](DATA_TRANSFER.md)은 그대로 유지하며 **두 종류를 모두 보관하려면 각각 내보내야 합니다.** 두 파일의 가져오기는 각각 독립된 트랜잭션입니다.

## 화면 사용법

1. **내 계정 → 데이터 관리 → 카탈로그 JSON 내보내기**에서 현재 계정의 저장한 카탈로그 전체를 다운로드합니다. 검색·종류·즐겨찾기·페이지 필터와 무관하며 원본 미연결 항목도 포함합니다.
2. **LoopShelf JSON 파일**을 선택하고 **파일 검사**를 누릅니다. 추가·동일·충돌·출처 연결 수와 원본 미연결로 복원할 수를 확인합니다.
3. 충돌이 없으면 **확인하고 가져오기**를 누릅니다. 기존 내용을 덮어쓰지 않고 새 개인 항목만 추가합니다. 동일 파일을 다시 가져오면 완전히 같은 항목은 건너뜁니다.
4. 검사 후 개인 자료나 참조 상태가 바뀌었거나 저장 응답을 받지 못했다면 다시 검사합니다. 성공 여부가 불명확한 쓰기를 자동 재전송하지 않습니다.

파일과 검사 결과는 브라우저 메모리에만 두며 로그아웃·계정 전환 시 제거합니다. 가져오기 뒤 저장한 카탈로그 목록을 다시 읽습니다. 원본 미연결 항목도 편집·즐겨찾기·검색·출처 해제·삭제·재내보내기가 가능합니다. 새 출처 연결과 원본 재연결 화면은 아직 지원하지 않습니다. 카탈로그 삭제에는 북마크의 60초 되돌리기가 없으므로 삭제 전 파일을 보관해야 합니다.

## 포맷과 한도

```json
{
  "format": "loopshelf-catalog",
  "schemaVersion": 2,
  "exportedAt": "2026-10-25T00:00:00.000Z",
  "items": []
}
```

내보내기는 v2입니다. 기존 v1(최상위 `sampleKind: synthetic`, 종류 없는 참조)도 엄격한 원래 형식으로 가져오며 내부에서 synthetic 참조로 정규화합니다. v2는 모든 원래/추가 참조에 종류를 요구합니다. 한 항목 안에서 자료 종류가 다른 출처를 연결하지 않습니다. 파일 버전/종류 변경은 기존 검사 토큰을 무효화합니다. [종류·호환성 상세](CATALOG_KINDS.md)

각 `items` 원소의 필드는 다음과 같습니다. 정확한 TypeScript 계약은 [catalog-transfer.ts](../src/shared/catalog-transfer.ts)에 있습니다.

| 필드 | 보존하는 내용 |
| --- | --- |
| `id` | 원래 개인 저장 UUID |
| `reference` | `entityId`, `kind`(album/track), `albumId`, 원래 `source` 참조, `sampleKind`(synthetic/live-capture) |
| `source` | SourceEntity `id`, `sourceId`(khinsider/zophar), `externalKey`, 정규 HTTPS `pageUrl` |
| `titleOverride`, `note`, `favorite` | 직접 지정한 제목 또는 null, 개인 메모, 즐겨찾기 |
| `createdAt`, `updatedAt` | 원래 생성·수정 시각, 밀리초 정밀도 ISO UTC |
| `sourceLinks` | 추가 앨범별 `reference`와 개인 판단 시각 `assertedAt` |

Track의 SourceEntity·URL은 소속 앨범의 출처입니다. 트랙 원본 키나 재생 리소스를 뜻하지 않습니다. canonical 제목·트랙 목록·길이·관찰·채택 근거·제거 영수증·음원·사용자 ID·인증·감사 기록·로컬 수정 버전은 내보내지 않습니다. 사용자가 직접 쓴 제목과 메모는 그대로 보존합니다.

파일당 **UTF-8 JSON 8 MiB, 개인 항목 5,000개, 항목당 추가 출처 20개**입니다. 가져온 뒤 해당 계정의 카탈로그 개인 자료 전체도 이 한도에 들어와야 합니다. 내보내기 한도를 넘으면 전체 오류이며 일부만 내보내지 않습니다. 빈 목록은 유효한 0건 작업으로 현재 선반을 지우지 않습니다. 큰 자료와 설치 전체 보존에는 [SQLite 백업](OPERATIONS.md)을 사용합니다.

엄격한 스키마로 알 수 없는 필드·잘못된 UUID/Unicode·시각 순서·비정규 URL·소스 키 불일치·중복 개인 ID/Entity·서로 다른 UUID 역할·모순되는 참조·중복 추가 출처·원래 출처 재연결·트랙 추가 출처를 거절합니다. private UUID, Entity UUID, SourceEntity UUID는 서로 다른 역할입니다. 같은 앨범을 별도로 저장하면서 다른 항목의 출처로 연결한 유효한 관계는 보존합니다.

## 참조와 충돌

가져오기에서 공유 `Entity`나 `SourceEntity`를 만들거나 수정하지 않습니다. 내부 UUID·종류·소속 앨범·소스 참조가 현재 관리 자료와 모두 일치할 때 기존 카탈로그에 개인 저장과 출처 판단을 복원합니다. 같은 URL·제목·소스 키라는 이유로 다른 내부 UUID에 대응시키지 않습니다.

한 항목의 원래 참조 또는 추가 출처 중 하나라도 현재 설치에 없으면 **그 항목 전체**를 개인 미연결 자료로 보존합니다. 원래 UUID·참조·개인 내용·출처 판단을 모두 유지하고 `contentState/presence: unresolved`로 표시합니다. 개인 제목이 null이면 `원본 미연결 앨범` 또는 `원본 미연결 트랙`을 표시하고 길이·순서는 null입니다. 나중에 카탈로그가 생겨도 자동으로 재연결하지 않으며 동일 파일의 재가져오기도 재연결 동작이 아닙니다.

현재 설치의 UUID가 다른 종류/참조로 사용 중이면 충돌입니다. 이미 존재하는 같은 개인 ID의 내용·시각·참조·연결이 다르거나, 같은 계정이 같은 Entity를 다른 개인 ID로 저장했거나, 추가 출처가 다른 개인 항목에 연결되어 있어도 전체 가져오기를 거절합니다. 다른 사용자의 개인 ID를 덮어쓰지 않으며 충돌 안내에는 업로드한 항목의 요약만 최대 50개 표시합니다.

원본이 누락·제거·차단된 경우에도 이미 보관한 개인 내용과 판단은 복원할 수 있습니다. 현재 설치의 제거 상태를 유지하고 공용 메타데이터를 되살리지 않습니다. 파일에는 다른 설치의 제거 영수증이 없으므로 이를 운영 결정의 이식으로 간주하지 않습니다. [전체 DB 복구 시 제거 결정 재적용](CATALOG_REMOVAL.md)도 계속 필요합니다. 개인 자료의 복원은 새 수집·재생·출처 추가 허용을 뜻하지 않습니다.

## HTTP·트랜잭션 계약

| 경로 | 동작 |
| --- | --- |
| `GET /api/library/catalog/export` | 쿼리 없음. 현재 계정 전체 JSON과 attachment 파일명 |
| `POST /api/library/import/preview` | `{ archive }`. `format`으로 북마크/카탈로그를 구분, 카탈로그 결과는 `scope: catalog`, `unresolvedCount` 포함 |
| `POST /api/library/import` | `{ archive, token }`. 추가 복원 후 `scope: catalog`, `added`, `skipped`, `connectionsAdded`, `unresolved` 반환 |

기존 실제 세션·Origin·선택적 `X-LoopShelf-Session` 사전 조건과 `no-store`를 적용합니다. 소유자는 서버 세션에서만 얻습니다. 파일 자체를 서버 디스크에 보관하지 않으며 입력 참조를 확인하려고 외부 요청을 하지 않습니다.

검사 토큰은 사용자·검증된 파일·현재 카탈로그 개인 스냅샷(수정 버전/미연결 여부 포함)·각 참조의 현재 연결 가능 여부와 가용/제거/누락 상태·10분 만료에 대한 HMAC입니다. 토큰은 인증을 대신하지 않습니다. 확인 시 `withDatabase` 경계 안의 동기 immediate 트랜잭션에서 다시 검사합니다. 다른 계정의 동시 ID 점유도 재검사하며 실패하면 개인 행·연결·감사 기록·버전 증가를 모두 롤백합니다.

기존과 동일한 행은 바꾸지 않습니다. 새로 복원하는 행은 `library_revision` 상한보다 큰 새 로컬 버전을 받아 삭제 전 편집 창의 쓰기를 거절합니다. 원래 연결 시각은 보존하되 감사 기록은 실제 복원 시각을 남깁니다. `invalid_archive`(400), `archive_too_large`(413), `preview_stale`/`import_conflict`(409)는 기존 이식 오류 계약을 공유합니다.

## DB와 검증

`0010_catalog_transfer.sql`은 `catalog_detached_item`과 `catalog_detached_link`를 추가합니다. 참조 ID는 없는 공용 행을 가리킬 수 있으므로 개인 JSON 참조로 보존하고 소유자/개인 항목에는 복합 FK를 적용합니다. 개인 정체성 불변, 기존 저장과의 ID/Entity 충돌, 일반/미연결 출처의 중복 점유와 20개 상한, 수정 버전 상한과 최소 감사 기록을 검사합니다. 0013은 기존 개인 참조를 다시 쓰지 않고 새 참조 종류 검사와 이전 앱 실행 제한을 추가합니다. 서버를 멈추고 [업그레이드 절차](OPERATIONS.md#업그레이드)에 따라 백업 후 `npm run db:migrate`를 실행합니다. 이번 검증에서는 운영 DB를 변경하지 않았습니다.

`tests/catalog-transfer.test.ts` 10개 테스트가 같은 설치/다른 설치 복원, 메타데이터 제외, UUID/시각/개인 판단 보존, 미연결 CRUD·소유권, 현재 제거/가용 상태, 오래된 검사·만료·다른 사용자 토큰, 동시 요청·실패 롤백, 엄격한 스키마·파일/누적 한도·페이지 밖 자료, 0009→0010 업그레이드와 전체 DB 백업/복원을 확인합니다. 기존 북마크 ID 충돌도 함께 검사합니다.

최초 v1 구현에서는 Node 152개·브라우저 11개를 통과했습니다. v2와 v1 호환을 포함한 2026-10-25의 최종 검증은 `npm run check`의 strict 타입 검사·빌드·Node **361개**와 `npm run test:e2e`의 **15개 시나리오**를 통과했습니다. 데스크톱/모바일 카탈로그 시나리오에서 실제 다운로드 파일 복원·검사 후 변경 거절·응답 유실 후 재검사·미연결 복원/재내보내기·충돌·개인 편집/해제/삭제를 검증했습니다. 임시 DB와 합성 자료를 사용했으며 실사이트 수집·실제 모바일 기기 검증은 포함하지 않습니다.

## 보관 수명 경계

[0012 보관 정리](CATALOG_RETENTION.md)는 snapshot 전에 실행합니다. 만료는 검사 토큰의 참조 상태를 바꾸며, 복원은 개인 ID/내용만 보존하고 만료된 외부 정보를 복원하지 않습니다. v1은 여전히 synthetic 전용입니다. v2는 live 참조의 종류와 개인 내용을 보존합니다. 이를 합성으로 표시하거나 일부 항목을 누락하지 않으며 원본이 없으면 미연결 상태를 유지합니다. 파일의 종류 주장은 공용 카탈로그나 수집/보관 정책을 바꾸지 않습니다.
