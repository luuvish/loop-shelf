# 합성 카탈로그 동시 요청과 DB 대기

현재 도구는 `--profile repeated|unique|sparse|blocked-prefix|boundary|deep|offset-deep`을 지원합니다. 기본 부하와 인증/시간 측정 계약은 유지하며, 각 분포의 독립 전체 SQL 기준/실제 행 수/정확한 페이지 검사는 [분포별 부하 검증](CATALOG_SEARCH_PROFILES.md)에 기록합니다. 0016의 실제 큰 offset과 마지막 커서 개선·v2 결과는 [후속 문서](CATALOG_OFFSET_SEARCH.md)를 따릅니다.

첫 개선 후 결과는 [검색 점유 시간 개선](CATALOG_SEARCH_OPTIMIZATION.md)에 있습니다. 아래는 개선 전 기준선입니다. 같은 동시 8개 부하의 전체 p95는 568.480→30.720ms로 줄었고 18개 조합 모두 300ms 이내입니다. 다른 제목 분포의 후속 고정 사례는 위 분포별 문서에 있으며 배포 수용량은 미완료입니다.

2026-10-25. 기존 [순차 검색 측정](CATALOG_PERFORMANCE.md)에 더해 두 실제 로그인 세션으로 검색·개인 조회·쓰기·세션 확인을 함께 실행합니다. 한 프로세스/한 SQLite 연결의 로컬 측정이며 배포 서버의 수용량 보장이 아닙니다.

## 재현과 격리

```sh
npm run bench:concurrency -- --output /tmp/loopshelf-concurrency.json
# 실행 계약 확인용 작은 자료
npm run bench:concurrency -- --albums 20 --tracks 3 --samples 3 --output /tmp/loopshelf-concurrency-smoke.json
```

기본값은 10,000앨범·앨범당 10곡·종류별 30표본입니다. 앨범 20–10,000, 곡 1–100, 표본 3–30을 받습니다. 동시성은 1·4·8, 종류별 워밍업은 2회로 고정합니다. 각 수준에서 6종류×30개인 180개, 총 540개 요청을 측정합니다. 작은 자료의 성공을 목표 규모 성능으로 사용하지 않습니다.

스크립트는 `.env`/`DATABASE_PATH`를 읽지 않고 OS 임시 폴더의 새 DB와 두 계정을 사용합니다. `--database` 같은 기존 DB 지정 옵션은 없습니다. 정상 종료와 예외에서 앱·DB를 닫고 임시 폴더를 제거합니다. 강제 종료 시 남은 임시 파일은 별도 정리가 필요할 수 있습니다. 출력은 새 파일만 생성하고 기존 파일을 덮어쓰지 않습니다. 실제 사이트·음원·운영 DB/계정을 사용하지 않습니다.

## 측정 방법

`catalog-scale-v1` 합성 자료를 기존 저장/개인 연결/JSON 서비스로 적재합니다. 기본 분포는 소스별 5천 앨범, 앨범마다 같은 10종의 곡 제목, 반복 표시 번호, 내 개인 자료 5천 개(미연결 100개 포함), 다른 계정 저장 1천 개와 추가 출처 100개입니다. 같은 연결과 예열된 OS 캐시를 사용하며 ANALYZE는 실행하지 않습니다. 적재·행 수/integrity/FK 검사·로그인·첫 커서 준비·실행 계획 추출은 표본 시간 밖입니다.

순서는 수록곡 검색 → 앨범 검색 → 개인 목록 → 개인 메모 수정 → 실제 세션 확인 → 앨범 상세의 고정 순환입니다. 매 순환마다 계정을 번갈아 사용하며 수록곡은 첫/다음 커서 페이지를 번갈아 읽습니다. 동시성만큼 모든 요청을 시작한 뒤 함께 완료될 때까지 기다리고 다음 묶음을 시작합니다. 마지막 묶음은 작을 수 있습니다. 요청 간 생각 시간·무제한 유입·지속 도착률을 흉내 내지 않습니다. 종류별 대기 위치가 영향을 받으므로 서로 다른 종류의 p95만으로 쿼리 비용을 비교하지 않습니다.

인증은 실제 비밀번호 로그인과 쿠키/세션 조건을 거칩니다. `Fastify.inject`의 전체 처리와 직렬화를 포함하지만 TCP·TLS·원격 네트워크·브라우저는 제외합니다. 기존 인증 제한을 완화하지 않습니다. `get-session`은 최대 3×(30+2)+초기 2회인 98회이며 한 종류의 실패/429를 빠른 성공 표본으로 취급하지 않습니다. 예상 밖 응답이나 결과 불일치는 측정 자체를 실패시킵니다.

원시 표본의 시간은 다음과 같습니다.

| 필드 | 범위 |
| --- | --- |
| `totalMs` | inject 호출 직전부터 응답 완료까지. DB 차례를 기다리기 전부터 측정 |
| `waitMs` | `acquireDatabase` 요청부터 이전 차례 종료 후 실행 재개까지. 큐와 실행 재개 지연 포함 |
| `heldMs` | DB 차례 확보부터 해제까지. 실제 세션 확인과 동기 저장소 작업 모두 포함하며 순수 SQL 실행 시간과 다름 |
| `outsideMs` | 전체 시간에서 대기/점유 합계를 뺀 나머지. 요청 처리·직렬화·DB 경계 밖 이벤트 루프 경합 포함 |
| `turns` | 해당 요청에 연결된 DB 차례 수. 현재 여섯 경로는 한 번이며 빠진 연결은 검사에서 거절 |

`src/database/access.ts`의 내부 진단 채널 `loopshelf.database.turn`은 구독자가 있을 때만 시계를 읽고 `{ waitMs, heldMs }`만 발행합니다. 큐 순서·동시 작업 수·인증/트랜잭션 경계는 그대로입니다. SQL·경로·내용·사용자·세션·쿠키를 발행하지 않으며 HTTP/env로 켜는 경로는 없습니다. 벤치마크의 `AsyncLocalStorage`로 요청을 연결하고 종료 후 구독을 해제합니다. 배경 정리는 요청 표본으로 오인하지 않습니다. 프로세스 내부 진단 구독자는 예외를 던지거나 DB 작업을 실행하지 않아야 합니다.

p50/p95는 nearest-rank입니다. 각 종류의 30개 원시 표본, 전체 처리량, 대기/점유/나머지 시간, 실행 환경, 소스와 마이그레이션 SHA-256, 대표 읽기 실행 계획을 보고서에 보관합니다. 표의 각 p95는 다른 요청에서 나올 수 있어 열별 p95를 더하면 전체 p95가 된다고 해석하지 않습니다. 측정 도구를 켠 비용도 포함합니다. `passed`는 18개 종류/동시성 조합의 전체 응답 p95가 모두 기존 참고 목표 300ms 이내인지이며, 초과만으로 CLI가 실패 코드를 반환하지는 않습니다.

## 최초 결과와 병목

최종 실행은 Apple M1 Ultra·20 논리 코어·128 GiB, Darwin 27.0.0, Node 24.21.0/SQLite 3.53.4, 약 245 MiB 디스크 DB, WAL/FULL·cache_size -16000에서 수행했습니다. 워밍업 2회 뒤 종류별 30개씩 측정했습니다. 전체 응답 p95는 동시 1개 **184.063ms**, 4개 **288.030ms**, 8개 **568.480ms**입니다. 종류별로는 18조합 중 12개만 300ms 이내이며 `passed: false`입니다. 실패/거절을 제외해 목표를 맞추지 않았고 측정된 540개 응답은 모두 정상 응답과 내용 검사를 통과했습니다.

| 요청 종류 | 동시 1개 p95 | 동시 4개 p95 | 동시 8개 p95 | 동시 8개 DB 대기 p95 | 동시 8개 DB 점유 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 수록곡 첫/다음 검색 | 194.725 | 187.267 | 470.974 | 289.315 | 188.813 |
| 앨범 검색 | 106.397 | 288.227 | 572.308 | 470.318 | 103.512 |
| 개인 목록 | 8.267 | 288.275 | 307.001 | 298.273 | 7.874 |
| 개인 메모 수정 | 2.723 | 290.122 | 574.244 | 572.408 | 1.658 |
| 실제 세션 확인 | 2.180 | 288.893 | 572.851 | 570.525 | 2.472 |
| 앨범 상세 | 3.711 | 8.303 | 302.613 | 297.463 | 3.302 |

단위는 ms입니다. 동시 1/4/8개 처리량은 각각 **20.203 / 20.644 / 20.522 요청/초**였습니다. 요청을 늘려도 처리량은 거의 늘지 않고 대기가 커졌습니다. 빠른 개인 수정과 세션 확인도 앞선 동기 검색 때문에 대기합니다. DB 점유 시간이 큰 수록곡/앨범 검색이 이 조건의 주요 병목이라는 판단이며, 순수 SQL별 비용이나 다른 하드웨어의 처리량을 확정한 것은 아닙니다.

[최종 원시 보고서](evidence/2026-10-25-catalog-concurrency-final.json)에 전체 표본·계획·환경·코드/스키마 체크섬을 보관했습니다. [예비 실행](evidence/2026-10-25-catalog-concurrency-pilot.json)에서 동시 4개의 종류별 최대 p95는 305.780ms였고 최종 실행은 290.122ms였습니다. 예비 실행의 개인 조회 계획은 별도 no-match 조회였으며 최종 보고서는 실제 측정한 첫 목록 계획으로 바로잡았습니다. 두 실행의 부하/제품 쿼리는 같고 성능 개선을 적용한 전후 비교가 아닙니다. 경계에 가까운 동시 4개 결과를 안정적인 배포 수용량으로 간주하지 않습니다.

이 작업은 DB 대기 계측과 재현 도구를 추가했으며 검색 SQL·인덱스·스키마·인증 제한·UI를 변경하지 않았습니다. 당시 다음 단계였던 검색 실행 계획/조회 범위 개선과 동일 부하 재측정은 [별도 문서](CATALOG_SEARCH_OPTIMIZATION.md)에 기록합니다. 인증을 DB 경계 밖으로 옮기거나 오래된 메타데이터를 제공해 시간을 줄이지 않습니다. 기존 순차 측정과 이번 동시 처리 목표를 모두 완료로 표시하지 않습니다.

## 정확성 검증과 한계

측정 중 공용 검색/상세는 준비한 현재 페이지와 정확히 비교하며 개인 목록은 해당 계정의 저장 ID만 허용합니다. 메모 수정은 같은 ID·새 버전·입력한 내용과 나머지 개인 필드 보존을 확인합니다. 측정 후 타 계정 조회/쓰기를 거절하고 기존 내용과 integrity/FK를 재확인합니다. 보고서는 쿠키·세션·계정 식별자·개인 내용을 담지 않습니다.

`tests/catalog-concurrency.test.ts`는 FIFO와 예외/중복 해제·진단 종료·동시 요청별 시간 분리, 분위 계산, 대기 중 보관 만료·원본 제거·세션 폐기와 타 계정 쓰기 거절, CLI의 전체 표본·임시 DB 정리·기존 파일/DB 보호를 확인합니다. 일반 CI는 시간을 합격 기준으로 쓰지 않습니다.

실제 휴대전화·Safari·원격 HTTPS·cold cache·저사양 하드웨어·여러 프로세스·다른 제목 분포·대량 보관 정리·실제 외부 소스 요청은 범위 밖입니다. 기존 큰 offset 지연도 별도 미완료입니다. 새로운 화면 변경이 없어 이번 단계에서는 브라우저 시나리오를 재실행하지 않으며 직전 UI 단계의 19개 결과와 구분합니다.

최종 검증에서 strict 타입·프로덕션 빌드·Node **427개**(신규 4개 포함)를 통과했습니다. 최종 보고서의 모든 코드 해시를 검사했고 직전 커서 보고서와 14개 마이그레이션 체크섬이 일치합니다. 테스트 성공은 동시 지연 목표를 달성했다는 뜻이 아닙니다.
