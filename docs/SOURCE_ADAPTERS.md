# 소스 Adapter와 메타데이터 캐시

2026-10-24 구현·오프라인 검증. KHInsider 검색과 Zophar 검색/상세의 전송 → 파서 → 정규화 DTO → SQLite 캐시를 연결했습니다. **실제 자동 수집·캐시 제공은 정책 미확인으로 비활성**입니다. 검증에서는 합성 응답과 별도의 내부 의존성을 사용하며 제품의 `sourceAssessments`를 바꾸지 않습니다. 후속 통합 검색 API/React 검색 화면과 [소스 상세 API](SOURCE_ALBUM.md)에 연결했습니다. 상세 화면·실제 카탈로그 적재는 아직 미연결입니다. [검색 API](SEARCH_API.md)

## 호출과 결과

`getSourceAdapters(db)`는 연결별 공용 Adapter를 반환합니다. 소스마다 `capabilities()`, `searchAlbums(query, signal?)`, `getAlbum(externalKey, signal?)`가 있습니다. 요청 주소·취소·DNS/IP·429 제한은 [전송 계약](SOURCE_TRANSPORT.md)을 사용합니다. 임의 URL, 사용자 ID·인증 헤더, 정책 우회 옵션은 받지 않습니다.

KHInsider의 상세 파서는 미지원입니다. capabilities에서 파서 지원, 표본 기술 상태, 정책 상태를 각각 표시합니다. 허용된 합성 계약에서 상세는 전송 없이 `unsupported`, 실제 제품에서는 우선 `policy_disabled`입니다. 페이지네이션은 미확인이고 발견한 다음 링크를 자동으로 취득하지 않습니다. 재생은 계속 `unsupported`/`unverified`입니다.

성공은 기존 `data / provenance / warnings`와 `delivery`를 반환합니다. `delivery.from`은 `transport` 또는 `cache`, `freshness`는 `fresh` 또는 `stale`이며 `freshUntil / expiresAt`을 포함합니다. 파서의 현재 페이지 보고 개수·추출 개수·부분 결과·미확인 상한을 유지합니다. `transport` 성공이 캐시 저장을 보장하지는 않습니다. 정책이나 응답 헤더가 저장을 금지하면 해당 응답만 반환합니다.

오래된 정상 값으로 대체할 때는 `refreshFailure`에 현재 갱신 실패를 함께 반환하고 기존 `capturedAt`, 파서 버전, 본문 해시와 경고를 보존합니다. TTL을 새로 시작하지 않습니다. 실패는 `ok: false, code, stage, httpStatus?, retryAt?`이며 raw HTML·내부 예외 문자열은 포함하지 않습니다. `stage`로 입력·정책·지원 상태·전송·파서·캐시 문제를 구분합니다. `policy_changed`, `content_removed`, `cache_error`도 별도 코드입니다.

`src/sources/metadata.ts`는 정규화 DTO의 공통 형식·출처·크기 검증입니다. 이 검증 자체는 이용 허가가 아닙니다. `src/catalog/input.ts`는 이를 사용하되 기존 `synthetic` 전용 저장 제한을 그대로 유지합니다. Adapter 응답을 공용 카탈로그에 자동 적재하거나 소스 간 동일성을 확정하지 않습니다.

## 정책과 캐시 식별

수집·캐시·표시 정책은 별도입니다. 표시가 비활성이면 캐시 제공·수집을 중단하고 해당 소스 캐시를 정리합니다. 캐시만 비활성이면 기존 캐시를 정리하되 수집/표시가 각각 허용된 현재 응답은 저장 없이 반환할 수 있습니다. 아직 fresh인 캐시는 같은 검토 버전에서 수집이 일시 차단되어도 캐시/표시 허용 여부를 따릅니다.

정책·기술 판단의 변경은 revision에 반영해야 합니다. 제품은 해당 소스 assessment 전체의 해시를 사용합니다. revision이 달라지면 과거 캐시를 fresh/stale 어느 쪽으로도 재사용하지 않습니다. 처리 도중 revision이 달라진 요청도 저장하지 않습니다. 표시/캐시 금지 정리는 요청 시 수행하며, 배포 시 정책 변경 전수 정리 작업은 아직 서버 시작/운영 UI에 연결하지 않았습니다.

논리 키는 소스 + 검색/상세 + 검색어/앨범 키 + sampleKind + parserVersion + policyRevision입니다. 검색어는 앞뒤 공백만 제거합니다. 대소문자·내부 공백·NFKC/플랫폼 차이를 임의로 합치지 않습니다. locale/filter/cursor는 아직 지원하지 않으며 향후 추가할 경우 반드시 키에 포함해야 합니다.

SQLite 물리 키는 소스·종류·요청 키·sampleKind이며 파서/정책 버전은 행의 일치 조건입니다. 같은 요청의 새 정상 값으로 교체합니다. 파서/정책 버전이 다른 마지막 정상 값은 최대 보관 시각까지 남을 수 있지만 제공하지 않습니다. 더 오래된 취득 시각의 늦은 응답은 더 최신 행을 덮어쓰지 않습니다. `synthetic`과 `live-capture` 네임스페이스가 분리되어 있으며 테스트에서 후자의 격리까지 검사한 것은 실제 자료 취득을 뜻하지 않습니다.

## 유효 기간과 보관 제한

| 결과 | fresh | 최대 보관/실패 대체 기간 |
| --- | --- | --- |
| 검색 정상/부분 결과 | 취득 후 6시간 | 취득 후 7일 |
| 앨범 상세 | 취득 후 7일 | 취득 후 30일 |
| 명시적인 검색 0건 | 취득 후 15분 | 동일한 15분, stale 대체 없음 |

이 값은 사이트가 승인한 quota나 보관 허가가 아닌 프로젝트 상한입니다. 실제 활성화 전 소스별 허용 기간을 검토해야 합니다. HTTP `no-store/private/no-cache`는 저장하지 않습니다. `max-age/s-maxage/Expires/Age`는 상한을 더 줄이며 `must-revalidate/proxy-revalidate`는 stale 제공을 막습니다. `Vary: *`나 현재 고정 요청 헤더 밖의 Vary도 저장하지 않습니다. 날짜 세 형식은 모두 UTC로 처리하고 잘못된 제한은 보수적으로 저장을 포기합니다. 조건부 요청·304 재검증·일반 HTTP 캐시 전체 구현은 아닙니다. [HTTP 캐시 지시의 원문](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2)

네트워크 오류·timeout·429·대기열 초과·5xx·파서 구조/응답 오류는 허용된 만료 전 정상 값으로 대체할 수 있습니다. 401/403 등의 차단, 404/410, challenge, 정책/버전 변경·삭제·호출자 취소는 stale 성공으로 숨기지 않습니다. 차단/없음 응답은 해당 요청 캐시를 지웁니다. 잘못된 저장 DTO·출처·TTL도 폐기 후 새 취득을 시도하며 0건을 만들어내지 않습니다.

`0011_source_metadata_cache.sql`은 정규화 메타데이터·최소 provenance·버전·수명만 저장합니다. HTML·오디오·표지·쿠키·개인 계정/메모는 저장하지 않습니다. 단일 DTO 상한 8 MiB, 전체 상한 200행/32 MiB이며 취득 시각이 오래된 행부터 제거합니다. 만료 행은 접근/쓰기 시 정리합니다. 이식용 개인 JSON에는 포함하지 않습니다.

모든 DB 접근은 `withDatabase`를 사용하고 쓰기/용량 정리는 짧은 동기 트랜잭션입니다. 네트워크·파서를 기다리는 동안 DB 경계를 잡아 두지 않습니다. 실패한 쓰기는 마지막 정상 행을 덮어쓰지 않습니다. 캐시가 사라져도 사용자 라이브러리 UUID에는 영향이 없습니다.

## 동일 요청과 취소

연결별 서비스에서 같은 논리 요청은 하나의 작업을 공유합니다. 각 호출자는 독립된 결과 복사본과 AbortSignal을 갖습니다. 한 호출자의 취소는 다른 호출자를 취소하지 않고, 마지막 호출자가 취소되면 공유 작업을 중단합니다. 이후 새 호출은 새 작업을 시작하며 취소된 작업의 늦은 결과는 저장하지 않습니다.

동시 논리 작업은 최대 16개, 작업별 구독자는 최대 32개입니다. 초과는 `queue_full`입니다. Adapter는 첫 호출부터 전체 12초 제한을 두며 DB 대기와 취소를 무시하는 의존성의 늦은 반환도 차단합니다. 전송의 10초 제한과 소스별 요청 간격은 별도로 유지합니다. 늦게 합류한 구독자는 기존 작업의 남은 시간을 공유합니다. 이것은 단일 Adapter 작업의 시간 예산입니다. 다중 소스 서비스의 별도 12초 대기 예산은 [통합 검색 계약](SEARCH_SERVICE.md)에서 검증했으며 HTTP 인증/취소 검증은 [검색 API](SEARCH_API.md)에 기록했고 UI 수용 검증은 남아 있습니다.

## 제거·업그레이드·복구

`catalog_removal`에 결정이 추가되면 같은 트랜잭션의 트리거가 해당 앨범 상세와 **그 소스의 모든 검색 캐시**를 삭제합니다. 다른 소스의 캐시와 개인 내용은 보존합니다. 캐시 읽기·갱신 완료·실패 대체 전에도 제거 결정을 검사합니다. 응답 검색 목록에 제거된 앨범이 들어 있으면 전체 응답을 `content_removed`로 거절하며, 필터링한 결과를 정상 0건으로 만들지 않습니다.

공용 카탈로그에서 아직 관리하지 않는 소스 키에 대한 독립적인 제거 명령, 정책 변경 전수 정리, 검색 UI 연동은 후속입니다. 과거 백업의 캐시는 별도 파일에서 자동으로 삭제되지 않습니다. 복구 전에는 기존 [제거 재적용 절차](CATALOG_REMOVAL.md)를 수행해야 합니다. 보관 기간과 정책 버전·현재 제거 상태를 다시 확인한 캐시만 제공할 수 있습니다.

기존 설치는 중지·백업 후 `npm run db:migrate`로 0011까지 적용합니다. 기존 마이그레이션·개인 테이블은 수정하지 않았습니다. 이번 작업에서는 임시 DB만 변경했으며 실제 운영 DB에 마이그레이션을 실행하지 않았습니다.

## 검증

`node --test tests/source-adapters.test.ts`의 **29개 테스트**와 전체 `npm run check`를 사용합니다. 정상/빈/부분 검색, 반복 트랙 번호, 정책·버전·TTL·오염된 캐시, stale/실패 구분, 크기/개수 상한, 요청 병합·취소·deadline·DB 경계, 제거 중 응답·늦은 관찰, 0010→0011 업그레이드·재시작·백업 복원을 포함합니다. 기존 카탈로그 합성 입력 제한과 개인 데이터 검증도 회귀 검사합니다.

UI 변경·실사이트 요청·실제 브라우저 CORS/오디오·배포 부하 검증은 수행하지 않았습니다. 후속으로 [내부 통합 검색 서비스](SEARCH_SERVICE.md)를 구현하고 다중 소스의 시간 예산·부분 결과·최종 정책/제거 검사·취소를 검증했습니다. 검색 API/React 검색 화면과 인증된 상세 API도 연결했으며 상세 화면과 실제 자료 적재는 남아 있습니다.
