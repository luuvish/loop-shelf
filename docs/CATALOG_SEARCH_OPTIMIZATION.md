# 검색의 DB 점유 시간 개선

이 문서는 0015와 첫 출처 후보 조회의 최초 검증 기록입니다. 이후 전체 정렬 순서의 곡 후보를 추가한 [분포별 검증](CATALOG_SEARCH_PROFILES.md), 현재 0016의 큰 offset과 마지막 페이지 개선은 [후속 문서](CATALOG_OFFSET_SEARCH.md)에 있습니다. 아래 수치는 이전 코드의 결과입니다.

2026-10-25. [동시 요청 측정](CATALOG_CONCURRENCY.md)에서 확인한 앨범/수록곡 검색의 점유 비용을 줄입니다. 인증·개인 소유권·보관 정리·현재 binding·정렬/커서·응답 DTO를 그대로 유지합니다. 실제 외부 수집이나 결과 캐시는 추가하지 않습니다.

## 비교한 방법

`scripts/bench-catalog-query-plans.ts`는 새 임시 DB에 0014 스키마와 합성 1만 앨범/10만 곡을 만들고, 보관한 이전 SQL을 동일 자료로 비교합니다. 같은 결과 행을 확인하며 SQL 준비/실행만 측정합니다. 워밍업 2회·표본 5개·동시 1개, 같은 연결/예열 캐시, ANALYZE 없음입니다. 인증·전체 응답 시간이 아닌 설계 선택용 예비 비교이며 30표본 서비스/API 결과와 구분합니다.

```sh
node scripts/bench-catalog-query-plans.ts --output /tmp/loopshelf-search-plan-probe.json
```

- 앨범 제목 인덱스는 매번 1만 앨범의 제목을 정규화하고 정렬하던 비용을 줄였습니다. 현재 정규화 제목·소스·원본 키·UUID 순서는 유지하며 같은 제목의 나머지 정렬만 수행합니다.
- 관찰 정보의 추가 covering index와 강제 사용, materialization 해제도 비교했으나 수록곡의 개선 폭이 작았습니다. 이 인덱스와 변경은 제품에 적용하지 않습니다.
- 수록곡은 정렬상 첫 제목과 앞선 출처 일부에서 페이지를 완성할 수 있는 경우, 전체 앨범 정보를 준비하지 않는 방식을 채택했습니다. 소수 후보가 충분하지 않으면 기존 전체 조회를 수행합니다.

[5표본 예비 비교](evidence/2026-10-25-search-query-probe.json)에서 수록곡 첫/다음 SQL은 185.536/183.545ms에서 6.145/6.459ms로, 앨범 첫 페이지 SQL은 100.223ms에서 0.111ms로 줄었습니다. covering index를 강제해도 수록곡은 161.156/172.174ms였으며 추가 보관 비용을 정당화할 정도의 개선으로 채택하지 않았습니다. 이 수치는 한 DB에서 후보들을 순서대로 비교한 결과이며 아래 실제 인증/전체 응답 수치와 구분합니다.

## 수록곡 후보 범위와 정확성

`src/catalog/track-query.ts`가 기존 전체/기준 행 조회와 새 후보 조회의 가용성·관찰 근거·현재 binding 검사를 공유합니다. `src/catalog/track-search.ts`는 같은 읽기 트랜잭션 안에서 다음 순서로 처리합니다.

1. 보관 정리를 수행하고, 커서가 있으면 현재 기준 곡의 정렬값/채택 근거를 다시 확인합니다. 예전과 같은 400/409 계약입니다.
2. offset이 0인 첫 페이지와 커서 조회에서는 기존 0014 제목 인덱스로 검색어에 맞는 가장 앞선 정규화 제목을 찾습니다. 커서는 기준 제목 이상만 읽습니다. 제목이 전혀 없으면 정상 빈 결과입니다.
3. 그 제목에 대해 `source_id, external_key` 순서의 앨범 출처 최대 256개를 후보로 읽습니다. 같은 제목을 이어 읽으면 기준 출처/키 이상부터 시작합니다. 이 수는 내부 조회 비용을 제한하며 사용자 결과 상한이 아닙니다.
4. 후보마다 합성 종류·가용성·제거·현재 제목/곡 관찰·Track Entity·현재 binding·원래 출처를 확인합니다. 현재 곡 제목과 후보 앨범의 UUID로 기존 제목 인덱스를 좁혀 읽습니다. 현재 위치와 UUID까지 같은 순서로 정렬합니다.
5. **limit+1개의 유효한 행을 얻었을 때만** 이 페이지를 사용합니다. 더 뒤의 출처나 더 뒤의 제목은 이미 확보한 행보다 앞설 수 없기 때문입니다. 경계 행으로 다음 커서도 정확히 계산합니다.
6. 후보가 부족하거나 모두 차단/누락된 경우에는 기존 전체 조회로 돌아갑니다. 일부 결과를 성공 0건/마지막 페이지로 오인하지 않고 다른 제목과 256개 뒤의 출처까지 확인합니다. 큰 offset 요청도 기존 전체 경로를 유지합니다.

후보 탐색의 제목은 개인 필드나 캐시에서 얻지 않습니다. 비가용 자료의 제목이 먼저 잡혀도 후보가 충분하지 않으면 전체 조회로 돌아가므로 현재 자료를 놓치지 않습니다. 페이지 경계에서 제목이 바뀌거나 현재 출처 안에 여러 같은 제목이 있어도 원래 정렬/커서 조건으로 처리합니다. 이름으로 행을 병합하거나 `track.position`을 현재 순서로 쓰지 않습니다.

희소 제목·비가용 자료가 많은 분포에서는 추가 후보 검사 뒤 전체 조회 비용을 함께 지불할 수 있습니다. 모든 자료 분포에 같은 가속을 보장하지 않으며 다른 분포별 부하 측정은 후속 범위입니다.

## 0015 업그레이드

`0015_catalog_album_search.sql`은 `album(normalize_search(title), id)` 파생 인덱스만 추가합니다. 공용/개인 UUID·내용·관찰 포인터·버전은 바꾸지 않습니다. 채택한 앨범 제목 갱신·보관 종료·원본 제거 시 SQLite가 같은 트랜잭션에서 인덱스를 갱신합니다. 새 검색 문서 테이블이나 FTS 동기화는 없습니다. 기존 0001–0014 SQL은 변경하지 않습니다.

업그레이드 전 백업 후 `npm run db:migrate`를 실행합니다. 실패한 배치는 인덱스와 이력을 롤백합니다. 이전 코드로 되돌릴 때는 해당 코드와 맞는 백업을 새 경로에 복원해야 합니다. 백업/복원 연결에도 기존의 결정적 `normalize_search` 함수를 등록하며 Unicode 정규화 변경 시 두 제목 인덱스의 재생성을 검토합니다. 운영 DB를 이 작업에서 업그레이드하지 않았습니다.

## 검증

`tests/catalog-search-optimization.test.ts`는 이전 보고서의 SQL을 독립 기준으로 사용합니다. 280앨범의 동등 Unicode 제목·반복 번호·두 소스 전체 순회, 앞선 256개 출처가 차단된 경우, 뒤쪽 출처의 유일한 제목, 후보가 적은 제목과 보관 만료를 대조합니다. 같은 ID/제목/순서와 앨범/곡의 별도 관찰 근거를 확인합니다. 새 스키마의 내용 보존·실패 롤백·현재 제목 갱신/제거와 검증된 새 경로 복원, 예비 도구의 임시 자료 정리도 검사합니다.

기존 수록곡 채택·커서 변경/만료/제거·실제 세션·대기 중 정책 변경·개인 정보 비노출과 DB 복원 검사는 유지합니다. 시간 임계값을 일반 CI의 합격 조건으로 사용하지 않습니다.
