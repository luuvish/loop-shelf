# 인증된 통합 검색 API

2026-10-24. `POST /api/search`를 기존 Fastify 서버에 연결했습니다. 실제 쿠키 로그인과 요청의 세션 조건을 확인한 후 [통합 검색 서비스](SEARCH_SERVICE.md)를 실행합니다. [React 검색 화면](SEARCH_UI.md)을 연결했습니다. **실제 사이트 수집·live 카탈로그 적재는 아직 미구현**입니다. 제품 소스 정책은 계속 `policy_disabled`이며 합성 카탈로그를 실제 검색 자료로 제공하지 않습니다.

## 요청

`POST /api/search`에 다음 JSON을 보냅니다. GET/HEAD/OPTIONS 검색 경로는 제공하지 않습니다.

```json
{
  "q": "星の記憶",
  "sources": ["khinsider", "zophar"],
  "limit": 12,
  "offset": 0
}
```

필요한 조건은 다음과 같습니다.

- 실제 `/api/auth/sign-in/email` 로그인 쿠키.
- 설정한 앱의 정확한 Host와 Origin. 다른 Origin·누락된 Origin은 거절합니다.
- `Content-Type: application/json` 및 **4 KiB 이하의 UTF-8 본문**.
- `/api/auth/get-session`으로 확인한 현재 세션 ID를 `X-LoopShelf-Session`에 전달. 검색에서는 이 조건이 필수입니다. 쿠키 인증 뒤 비교하므로 ID만으로 로그인하거나 사용자를 선택할 수 없습니다.
- URL query는 비워 둡니다. 검색문을 URL에 기록하지 않습니다. body/query의 userId, sampleKind, 정책·전송 설정, 임의 URL 등은 받지 않습니다.

입력 검증은 내부 서비스와 같은 `src/search/input.ts`를 사용합니다. 검색문 최대 200자·제어 문자 거절·앞뒤 공백 제거, 소스 최대 2개·중복 금지, limit 1–100/offset 0–100,000 규칙을 유지합니다. 문자열로 보낸 숫자는 받지 않습니다. `sources` 생략 시 외부 소스를 요청하지 않으며 limit/offset은 로컬 페이지에만 적용합니다.

이 API는 개인 저장을 만들거나 수정하지 않습니다. 사용자별 북마크·메모 검색은 기존 별도 API의 역할입니다. 검색 결과를 저장하려면 후속 UI/적재 계약에 따른 명시적 동작이 필요합니다.

## 응답

HTTP 200은 통합 검색 봉투를 전달했다는 의미입니다. `status: complete | partial | failed`와 각 부분의 `ok`, 실패 코드, provenance, 캐시 상태를 확인해야 합니다. 실패를 정상 0건으로 바꾸지 않습니다. 전체 모양은 `src/shared/search.ts`와 [서비스 계약](SEARCH_SERVICE.md)을 따릅니다.

현재 실제 제품에 위 요청을 보내면 `sampleKind: live-capture`, `status: failed`, 로컬 `sample_kind_unavailable`, 선택한 소스 각각 `policy_disabled`를 받습니다. 이는 검색 인덱스에 결과가 없다는 뜻이 아닙니다. 외부 사이트 요청이나 합성 fixture 적재를 발생시키지 않습니다.

성공적으로 세션을 재확인한 응답에는 `X-LoopShelf-User`와 `X-LoopShelf-Session`을 설정합니다. 브라우저는 응답 세션과 현재 화면의 세션이 같은지 확인한 뒤 결과를 적용해야 합니다. 세션 거절 응답에는 사용자/세션 표시 헤더나 검색 결과를 보내지 않습니다.

모든 응답은 `Cache-Control: no-store`입니다. 검색 처리 응답에는 `Vary: Cookie, X-LoopShelf-Session`도 설정합니다. 기존 Service Worker는 POST/API/개인 자료를 캐시하지 않으며 오프라인 검색 요청을 저장하거나 재전송하지 않습니다.

| HTTP | 코드/내용 | 의미 |
| --- | --- | --- |
| 200 | 검색 봉투 | 로컬/소스별 성공·실패를 독립적으로 확인 |
| 400 | `invalid_input`, `invalid_request`, `invalid_host` | 입력/JSON/Host 오류 |
| 401 | `unauthorized`, `session_changed` | 로그인 없음·만료·폐기 또는 요청의 세션 조건 불일치 |
| 403 | `invalid_origin` | 앱과 일치하지 않는 Origin |
| 413 | `invalid_request` | 본문 바이트 상한 초과 |
| 415 | `invalid_content_type` 또는 `invalid_request` | JSON이 아닌 본문 |
| 428 | `session_required` | 유효한 쿠키는 있지만 세션 조건 헤더 없음 |
| 429 | `rate_limited`, `queue_full` | IP별 요청 횟수 또는 동시 작업 한도 초과 |
| 408 | `cancelled` | 서비스가 명시적 취소를 반환한 경우. 끊어진 연결에는 응답하지 않음 |
| 503 | `server_closing` | 서버 종료로 검색 중단 |
| 504 | `search_timeout` | 세션 확인·검색·최종 검사 대기 예산 소진, 보유 결과 폐기 |
| 500 | `internal_error` | 내부 오류, 예외 메시지·쿼리·인증 세부 내용 비노출 |

서비스 수준 거절(`invalid_input`, `queue_full`, `cancelled`)은 기존 `{ ok: false, code }` 형식을 유지합니다. HTTP 경계에서 발생한 오류는 `{ code }` 형식입니다. 부분 소스의 403/429/timeout은 그 소스의 결과 안에 남으며 다른 유효 결과까지 HTTP 오류로 바꾸지 않습니다.

## 세션·DB·취소

1. 본문을 수신·파싱한 뒤 검색 handler에 들어오면 **12초 비동기 대기 제한**을 시작합니다. 최초 인증 DB 큐, 검색, 마지막 인증 DB 큐 모두 같은 제한을 공유합니다. 내부 검색의 11초 소스/12초 전체 예산도 유지하지만 HTTP 남은 예산이 더 짧으면 HTTP 취소가 우선합니다.
2. `withDatabase`에서 실제 쿠키 세션을 확인합니다. 검색용 조회는 쿠키 캐시와 세션 수명 연장을 비활성화합니다. 헤더 조건과 입력을 검사한 뒤 DB 경계를 해제하고 검색합니다.
3. 검색 중에는 같은 연결로 북마크 작업·로그아웃·운영자 비밀번호 재설정이 진행될 수 있습니다. 검색이 반환되면 다시 `withDatabase`에서 원래 요청의 세션 존재·만료·소유자·세션 ID를 확인합니다. 로그아웃이나 재설정으로 폐기되었다면 결과를 버리고 401을 반환합니다.
4. 마지막 인증 대기 동안 메타데이터가 만료/제거되거나 정책이 바뀔 수 있으므로, 같은 DB 경계 안에서 `service.recheck(input, result)`로 노출 상태도 다시 검사합니다. 허용한 현재 결과만 응답 전송을 시작합니다. FastifyReply를 DB callback에서 반환하여 소켓 전송 완료까지 DB를 점유하지 않도록 합니다.
5. 클라이언트 연결이 끊기면 해당 검색의 AbortSignal을 취소합니다. 정상 POST 본문 수신 완료에 발생할 수 있는 요청 close를 취소로 오인하지 않으며 응답 연결 close와 요청 aborted를 사용합니다. 서버 종료도 모든 진행 중인 검색을 취소합니다.
6. 중단된 인증 큐 작업은 나중에 DB 경계를 얻어도 조회 전에 종료합니다. 중단을 무시하고 늦게 반환한 서비스 응답은 최종 검사나 전송으로 이어지지 않습니다. 다른 요청이 공유하는 Adapter 구독은 기존 서비스 계약에 따라 유지됩니다.

HTTP 요청의 쿠키는 요청 시작 시 고정됩니다. 서버는 다른 창에서 **새 쿠키를 발급받았다는 사실만으로** 이미 유효한 다른 세션을 무효화하지 않습니다. 로그아웃 없이 별도 세션에 로그인한 경우에는 두 세션 모두 정상일 수 있습니다. 따라서 React 화면은 로그아웃·계정 전환 때 진행 중인 요청을 취소하고 메모리 상태를 지우며, 응답의 세션 ID를 현재 상태와 비교해야 합니다. API 검증은 로그아웃 후 전환·폐기/만료와 오래된 조건 헤더 거절을 포함합니다. 현재 React 클라이언트는 응답 헤더 비교 뒤 현재 쿠키로 세션을 다시 조회하며, 두 확인 중 하나라도 실패하면 결과를 표시하지 않습니다. 다른 계정 쿠키가 발급되는 동안 이전 응답이 도착하는 경합도 브라우저에서 검증했습니다. [취소·세션·화면 계약](SEARCH_UI.md)

로그아웃이 진행 중인 검색을 즉시 서버 푸시로 중단시키는 기능은 추가하지 않았습니다. 서버는 결과 전송 전 폐기 상태를 확인하며 클라이언트가 요청을 취소하면 즉시 해당 구독을 해제합니다. 이미 전송한 응답을 소급 회수하지 않습니다. 동기 JavaScript/SQLite 실행과 요청 본문 수신 자체는 선점형 12초 제한의 대상이 아닙니다.

## 제한과 검증

검색 API·`POST /api/source-album`·`POST /api/source-album/save`는 `src/server/source-read.ts`의 공통 제한을 사용합니다. 신뢰하지 않는 프록시 헤더 대신 실제 연결 IP를 기준으로 세 경로를 **합쳐 분당 30회**를 허용합니다. 동시 handler도 세 경로를 합쳐 서버 인스턴스당 **16개**이며 인증 대기를 포함합니다. 경로를 바꿔 한도를 늘리지 못합니다. [상세 API와 공통 경계](SOURCE_ALBUM.md) 제한 초과는 자동 대기/재시도 없이 반환합니다. IP 횟수 제한 응답의 `Retry-After`를 존중하고, 실제 소스의 제한은 이 앱 제한과 별도로 유지합니다. 이 수치는 사이트가 승인한 quota가 아닙니다.

`tests/search-api.test.ts`의 **21개 테스트**는 임시 SQLite와 두 실제 계정/쿠키 세션을 사용합니다. 인증/세션 조건·Origin/Host·입력/크기·요청 제한, 대기 중 CRUD/로그아웃/전환/만료/비밀번호 재설정, 전체/DB 대기 timeout, 종료·예외·합성 자료 비노출을 검증합니다. 그중 2개는 `127.0.0.1`의 임시 포트에 실제 서버를 열어 정상 본문 수신과 연결 종료를 검사합니다. 인증 우회나 테스트용 HTTP 설정은 추가하지 않았습니다. 지연은 테스트에서 내부 검색 함수만 대체합니다.

서비스 테스트 3개를 추가해 인증 대기 후 정책·만료·제거/현재 로컬 값과 요청 문맥을 다시 검사했습니다. **`npm run check`: strict 타입 검사·프로덕션 빌드·총 268개 Node 테스트 통과.** 실제 사이트·운영 DB·계정을 사용하지 않았으며 스키마/인증 패키지 설정을 바꾸지 않았습니다. 상세 API 추가 시 공통 인증 경계로 추출한 뒤 기존 검색 API 21개와 전체 301개 Node 테스트·13개 브라우저 시나리오를 다시 통과했습니다. 후속 React 검색/상태/재시도 화면과 브라우저 검증은 [검색 화면 문서](SEARCH_UI.md)에 기록합니다.
