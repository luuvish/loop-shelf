# LoopShelf

**게임 음악을 발견하고, 나만의 선반에.**

프로젝트명은 **LoopShelf(루프셸프)**, 저장소 식별명은 **`loop-shelf`**입니다.

원격 저장소: [luuvish/loop-shelf](https://github.com/luuvish/loop-shelf)

여러 게임 음악 아카이브를 검색하고, 게임·앨범·곡을 탐색하며, 외부 서비스의 변화와 독립적으로 개인 라이브러리를 유지하는 웹 애플리케이션입니다. 현재 소스 검증 도구와 계정별 개인 북마크 웹 앱을 구현했습니다.

## 현재 상태

**2026-10-25: 소스 접근 검토 계약을 구현했습니다. 실제 자동 수집·live 저장은 비활성입니다.**

수집 허가·robots 경로 검토·공식 요청 한도를 분리하고 정확한 URL/쿼리·기한·현재 정책에 묶었습니다. 검토가 누락되거나 만료·교체되면 요청과 결과를 거절하며, 현재 지킬 수 없는 기간별/공통 그룹 한도도 거절합니다. robots는 수동 검토 결과를 기록하는 단계로 자동 파서나 실제 사이트 허가 취득은 포함하지 않습니다. 합성 근거 24개를 포함한 타입·빌드·Node 486개와 관련 검색/복구 브라우저 3개를 검증했습니다. [계약·검증·남은 조건](docs/SOURCE_ACCESS_REVIEW.md)

이전 0017에서 같은 로컬 DB를 쓰는 여러 프로세스가 소스별 요청 간격·429 대기·대기열을 공유하도록 했습니다. 재시작 후에도 제한을 유지하고, 종료 여부가 불확실한 요청은 자동 해제하지 않습니다. 운영자 조회/복구/대기 연장 및 같은 호스트/DB·시계 전제는 [운영 계약](docs/SOURCE_COORDINATION.md)을 따릅니다.

0016 단계의 합성 1만 앨범·10만 곡, M1 Ultra·예열 캐시의 순차 42개 측정이 모두 p95 300ms 이내였습니다. offset 99,900의 조회는 1,215.498→18.214ms, 마지막 커서 페이지는 146.735→34.206ms로 줄었습니다. 0016은 현재 검색 순서를 별도 유지하고 선택 페이지의 원본 근거를 다시 확인합니다. 저장 공간·갱신·시작 검증 비용도 늘어나므로 측정 조건과 유지보수 절차를 함께 기록했습니다. [구조·성능·운영](docs/CATALOG_OFFSET_SEARCH.md) 앞선 여섯 분포의 108조합 결과는 [이전 스키마 측정](docs/CATALOG_SEARCH_PROFILES.md)으로 구분합니다.

합성 카탈로그에서 현재 채택된 곡 제목을 검색하며 한일문 1–2자·리터럴 부분 검색, 반복 표시 번호·미확인 길이·앨범/곡의 별도 관찰 근거를 유지합니다. 개인 메모와 누락/제거/만료 자료는 검색하지 않습니다. 0014 제목 인덱스와 0016 현재 검색 목록은 기존 ID/내용을 유지하며 업그레이드·백업·복원을 검증했습니다. `nextCursor`로 다음 페이지를 이어 읽으며 기준 곡이 삭제/만료/재채택되면 새 검색을 요구합니다. **저장한 카탈로그 → 수록곡 검색**에서 검색·이전/다음·자료 근거를 확인하고 앨범에서 곡을 저장할 수 있습니다. [화면 사용법](docs/CATALOG_TRACK_UI.md) [수록곡 검색 계약](docs/CATALOG_TRACK_SEARCH.md)

상세 관찰의 fingerprint·별도 보관 허용·현재 세션을 다시 확인한 뒤 공용 카탈로그와 개인 저장을 함께 반영하는 내부 흐름을 추가했습니다. 합성 자료와 실제 임시 쿠키 세션으로 중복 ID/개인 내용 보존·변경 트랙 검토 보류·전체 롤백·조회 중 제거/만료/로그아웃을 검증했습니다. `POST /api/source-album/save`와 상세의 저장 가능 여부/fingerprint를 연결했습니다. React 상세에서 저장 가능 여부·기한을 확인하고 개인 제목·메모·즐겨찾기를 명시적으로 저장합니다. 중복은 기존 내용을 유지하며 변경/응답 유실 뒤 선반과 상세를 재확인합니다. 검색·상세·저장의 요청 한도와 현재 쿠키 검사를 유지합니다. [저장 화면 계약](docs/SOURCE_SAVE_UI.md) live 자료는 합성 저장소에 들어가지 않습니다. [저장 HTTP 계약](docs/SOURCE_SAVE_API.md) · [입력·정책 계약](docs/SOURCE_SAVE.md)

로컬 카탈로그와 선택한 소스 Adapter의 결과를 구분하는 내부 통합 검색 서비스를 구현했습니다. 취득 근거·캐시·부분 실패를 보존하고 12초 예산, 취소, 응답 직전의 정책/만료/제거 재검사를 검증했습니다. 합성 자료와 실제 자료를 분리하며 개인 북마크·메모를 공용 검색에 포함하지 않습니다. `POST /api/search`에 연결하고 실제 세션의 최초/최종 확인·Origin·요청 제한·연결 종료 취소를 검증했습니다. React의 음악 검색 화면에서 소스를 직접 선택하고 결과·정책 상태·캐시/부분 실패를 확인하며 명시적으로 재시도할 수 있습니다. 취소·오프라인 복귀·응답 세션과 현재 쿠키 재검사도 검증했습니다. [검색 화면 계약](docs/SEARCH_UI.md) [통합 검색 계약](docs/SEARCH_SERVICE.md) · [검색 API](docs/SEARCH_API.md)

`POST /api/source-album`으로 소스와 앨범 식별명을 지정해 상세를 조회하는 서비스·API를 추가했습니다. 수록 순서·반복 표시 번호·미확인 값과 취득 근거를 보존하며 검색과 인증/취소·합계 분당 30회/동시 16개 한도를 공유합니다. 서비스 18개·API 15개 테스트와 기존 화면 회귀를 통과했습니다. 현재 제품 응답은 정책 비활성이며 성공 검증은 합성 자료만 사용했습니다. 검색 결과의 상세 보기로 React 앨범/수록곡 화면도 연결했습니다. 원문 주장·캐시/실패·취소·기한 만료·현재 쿠키 전환을 구분하며 실제 카탈로그 적재/개인 저장은 후속입니다. [상세 화면 계약](docs/SOURCE_ALBUM_UI.md) [상세 조회 계약](docs/SOURCE_ALBUM.md)

정책·주소·요청 제한을 갖춘 전송 계층에 검색/상세 Adapter와 SQLite 캐시를 연결했습니다. 정상 0건·부분 결과·갱신 실패를 구분하고, 정책/파서 버전·유효 기간·콘텐츠 제거를 확인합니다. 동일 요청 병합과 호출자별 취소도 검증했습니다. 검색 API와 React 검색 화면을 연결했으며 카탈로그 자동 적재는 아직 미연결입니다. [Adapter·캐시 계약](docs/SOURCE_ADAPTERS.md) · [전송 계약](docs/SOURCE_TRANSPORT.md)

이메일/비밀번호 로그인 후 KHInsider·Zophar 앨범 URL을 직접 북마크하고 제목·메모·즐겨찾기를 관리할 수 있습니다. 반응형 화면에서 내 북마크 검색·페이지 이동·추가·편집·삭제, 계정 조회와 소스 이용 안내를 제공합니다. 저장한 북마크 여러 개를 내 선반에서 한 항목으로 연결하고 해제할 수 있으며, 각 원래 ID·제목·메모·즐겨찾기를 보존합니다. 중복 저장, 변경 충돌, 통신 실패, 세션 만료·계정 전환도 처리합니다. 내 계정의 데이터 관리에서 JSON 내보내기, 복원 전 검사와 원래 ID·개인 내용·출처 연결을 보존하는 가져오기를 제공합니다. 삭제 후 60초 동안 같은 로그인 세션에서 원래 ID와 내용을 되돌릴 수 있습니다. 기본 PWA 설치 정보와 정적 앱 셸, 오프라인 안내, 기존 창 종료 후 적용하는 업데이트도 제공합니다. 개인 API·인증·음원은 캐시하지 않습니다. 실제 외부 자료 수집과 재생은 아직 제공하지 않습니다.

앞선 KHInsider 검색 202건과 Zophar 검색/상세의 표본 검증은 유지합니다. KHInsider 상세는 403이며 두 사이트의 자동 수집·캐시·표시 허가는 미확인이므로 제품 자동 연동은 계속 `policy_disabled`입니다. 수동 북마크는 외부 요청 없이 동작합니다. [소스 검증 결과](SOURCES.md#단계-1-구현-검증-결과)

내부 카탈로그 서비스는 합성 파서 DTO를 소스별 Album·Track·SourceEntity로 저장하고, 반복 입력에서도 UUID와 provenance를 유지합니다. 원본 키가 없는 트랙 목록이 달라지면 기존 곡을 자동 덮어쓰지 않고 검토 필요 상태로 남깁니다. 실제 수집 자료는 받지 않으며 합성 카탈로그만 앱에서 탐색할 수 있습니다. [저장·재수집 계약](docs/CATALOG.md)

카탈로그 개인 API는 관리 앨범·트랙의 저장·검색·메모·즐겨찾기와 같은 자료 종류의 앨범 SourceEntity 연결/해제를 지원합니다. 합성 자료와 외부 자료 참조를 구분하고, 만료·제거·원본 미연결 상태에서도 개인 내용과 종류를 유지합니다. 새 JSON은 각 참조의 종류를 담은 v2이며 기존 v1 파일도 가져올 수 있습니다. [자료 종류·이식 계약](docs/CATALOG_KINDS.md) **저장한 카탈로그** 화면에서 목록·검색·종류/즐겨찾기 필터·개인 제목/메모 편집·삭제·출처 조회/해제를 제공합니다. 현재 원본 제목을 읽고 사용자가 지정한 제목만 개인 내용으로 저장하며, 만료·누락·제거 상태와 자료 종류를 표시합니다. 충돌·응답 유실 후 최신 값을 확인하고 계정 전환 시 초안을 제거합니다. **카탈로그 둘러보기**에서 관리 중인 합성 앨범·현재 수록곡을 탐색하고 새로 저장할 수 있으며, 출처 보기에서 추가 앨범을 직접 선택해 연결합니다. [탐색·저장 계약](docs/CATALOG_BROWSE.md) 카탈로그 개인 자료는 별도 JSON으로 내보내고 복원합니다. 다른 설치에 원본이 없으면 미연결 항목으로 개인 내용과 참조 ID를 보존합니다. 기존 북마크 JSON v1과 60초 삭제 복구는 직접 입력 북마크 전용입니다. [카탈로그 이식 계약](docs/CATALOG_TRANSFER.md) [화면 사용법](docs/FRONTEND.md#저장한-카탈로그-관리) · [API와 지원 범위](docs/CATALOG_LIBRARY.md)

`catalog:review`와 `catalog:adopt`로 변경된 목록을 검토하고 명시적인 ID 대응을 적용할 수 있습니다. 순서 변경·새 트랙·누락·재등장을 처리하며 개인 저장 ID와 내용을 보존합니다. 오래된 검토·중복/불완전한 매핑은 거절하고 같은 요청의 재시도는 새 ID를 만들지 않습니다. [운영 명령과 대응 계약](docs/TRACK_ADOPTION.md)

운영자용 `catalog:remove` 명령은 관리 중인 소스 앨범의 관찰·메타데이터를 제거하고 재적재를 차단합니다. 앨범·트랙·개인 저장 UUID와 사용자 메모·즐겨찾기는 보존합니다. 공유·수동 자료가 있으면 검토가 필요하다는 오류를 반환하며, 기존 백업의 콘텐츠까지 지우지는 않습니다. [제거 범위와 복원 시 처리](docs/CATALOG_REMOVAL.md)

최신 DB 스키마는 0017입니다. 기존 설치는 [업그레이드 절차](docs/OPERATIONS.md)에 따라 백업 후 `npm run db:migrate`를 실행합니다. 검색 목록의 손상이 확인된 경우 운영자 `npm run catalog:reindex`로 파생 목록을 재생성·검증할 수 있습니다. 소스 요청 상태는 `npm run source:requests -- inspect --source zophar`로 확인합니다. 운영 DB에 이번 변경을 자동 적용하지는 않았습니다.

## 제안 방향

1. KHInsider와 Zophar의 연동 가능성을 먼저 검증합니다. 현재 두 사이트의 검색 HTML은 확인했지만, KHInsider 앨범 요청에서 403 차단이 발생했고 자동 수집 허용 범위도 미확인입니다.
2. 음악의 정체성과 외부 페이지·재생 리소스를 분리합니다. 원본 URL이 사라져도 사용자 저장 항목의 내부 ID는 유지합니다.
3. 첫 MVP는 검색, 앨범과 수록곡 탐색, 계정별 저장·즐겨찾기, 직접 URL 북마크, 반응형 UI, 기본 PWA입니다.
4. 허용 범위를 확인한 소스만 자동 수집을 활성화합니다. 차단된 소스는 캐시 상태와 원문 링크를 표시하며, 검색 실패를 결과 없음으로 처리하지 않습니다.
5. 스트리밍·플레이리스트·자동 청취 기록은 다음 단계입니다. 외부 페이지를 열었다는 이유만으로 재생 이력을 만들지 않습니다.

기술 기준안은 React + Vite, TypeScript 서버(Fastify), SQLite + FTS5입니다. 소규모 비공개 셀프호스팅과 단일 서버를 출발점으로 삼되, MVP 완료 조건에 사용자별 데이터 격리를 포함합니다. Decl은 추후 실험 대상으로 두며 첫 MVP의 필수 의존성이 아닙니다.

## 개발 및 오프라인 검증

Node.js **24.12 이상**, 권장·검증 버전은 **24.21.0 LTS**([.node-version](.node-version))입니다. better-sqlite3 **13.0.3**의 SQLite **3.53.4**, Fastify **5.12.7**, Better Auth **1.7.10**, TypeScript **7.0.2**, React **19.3.1**, Vite **8.3.5**를 사용하며 모든 직접 의존성 버전을 고정했습니다. 서버는 Node의 내장 TypeScript type stripping으로 실행하고 브라우저는 Vite로 빌드하며 타입 검사는 별도로 수행합니다. [Node 문서](https://nodejs.org/api/typescript.html)

```sh
npm ci --ignore-scripts
npm run check
```

`npm run check`의 서버·브라우저·worker strict 타입 검사, 프로덕션 빌드와 **438개 Node 테스트**를 통과했습니다. 외부 사이트 요청 없이 파서, 실제 SQLite, 인증된 API, 운영 CLI와 복원, 정적 파일 제공을 확인합니다. 브라우저 검증은 `npx playwright install chromium` 후 `npm run test:e2e`로 실행하며 직전 UI 단계에서 전체 **19개 시나리오**를 통과했습니다. 이번 검색 개선 단계에서는 수록곡 검색·개인 카탈로그의 데스크톱/모바일과 백업 복구 5개를 재실행해 통과했습니다. 수록곡 검색의 데스크톱/모바일 검색·커서 이동·현재 곡 저장·유실 복구·기한/세션 검사와 기존 통합 검색·소스 상세/저장·북마크·PWA·백업 복구를 포함합니다. 임시 DB에서 실제 세션을 사용하며 운영 계정을 생성하지 않습니다. 인증 라이브러리의 여러 런타임용 선언 파일 때문에 `skipLibCheck`를 사용하지만 프로젝트 소스의 strict 검사는 유지합니다.

전체 규모의 성능 측정은 `npm run bench:catalog -- --output /tmp/loopshelf-catalog-report.json`으로 별도 실행합니다. 새 임시 DB를 만들고 종료 시 정리하며 운영 DB와 외부 사이트를 사용하지 않습니다. 이번 조회 개선에는 추가 마이그레이션이 없습니다.

이번 Adapter·캐시 작업에서는 전체 `check`와 새 29개 테스트를 통과했고, 임시 DB에서 0011 업그레이드·재시작·백업 복원을 검증했습니다. 운영 DB는 변경하지 않았습니다. 화면 변경은 없으며 Playwright 11개는 앞선 카탈로그/성능 단계의 통과 기록입니다.

## 앱 실행

처음 한 번 `.env.example`을 `.env`로 복사하고 `BETTER_AUTH_SECRET`에 무작위 비밀값을 설정합니다. 생성 명령과 상세 설명은 [백엔드 사용법](docs/BACKEND.md)에 있습니다.

```sh
npm run db:migrate
npm run account:create -- --email you@example.com --name 'Your name'
npm run build
npm start
```

기존 설치는 서버를 멈추고 `npm run db:migrate`로 `0011_source_metadata_cache.sql`까지 적용한 후 실행합니다. 변경 전 자동 백업을 만들며 기존 북마크를 보존합니다. [전체 업그레이드 절차](docs/OPERATIONS.md#업그레이드)

계정 명령은 비밀번호를 숨겨 입력받습니다. 브라우저에서 `http://127.0.0.1:3000`을 열어 로그인합니다. `/api/health`, `/api/auth/sign-in/email`, `/api/bookmarks`도 같은 origin에서 제공합니다. 공개 회원가입은 비활성입니다. 개발 중에는 `npm start` 대신 `npm run dev`를 사용하면 같은 주소에서 Vite 변경 반영을 사용할 수 있습니다.

## 백업과 복구

```sh
npm run db:backup -- --output .local/backups/manual-20261022.sqlite
```

실행 중인 DB도 커밋된 WAL을 포함해 백업하며 출력 파일은 새 이름이어야 합니다. 복구는 서버를 멈춘 뒤 실행합니다.

```sh
npm run db:restore -- --input .local/backups/manual-20261022.sqlite --output .local/loopshelf-restored-20261022.sqlite
```

성공 후 `.env`의 `DATABASE_PATH`를 복원본으로 바꾸고 `npm run db:migrate`를 실행합니다. 백업 이후의 카탈로그 제거 결정이 있으면 서버 시작 전에 재적용합니다. **복구 후 모든 사용자는 다시 로그인해야 합니다.** 복원본의 세션·임시 인증 정보·삭제 복구 영수증을 제거하며 북마크 ID·개인 내용·출처 연결을 보존합니다. 원본 DB와 백업은 변경하지 않습니다. 계정·비밀번호도 백업 시점으로 돌아갑니다. [복구 후 확인 및 문제 대응](docs/OPERATIONS.md#새-db-경로로-복구)
